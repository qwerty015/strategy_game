# Правила разработки

## Архитектура

Игровая логика не импортирует Ebitengine. Пакеты `building`, `economy`,
`logistics`, `villagers`, `pathfind`, `resource`, `save` и `i18n` должны
оставаться тестируемыми без окна и GPU.

Пакеты `render`, `ui` и `cmd/game` отвечают за экран, ввод и связывание
подсистем.

## Документирование кода

- у каждого экспортируемого типа и метода должен быть Go-комментарий;
- комментарии описывают игровое правило или контракт, а не очевидную строку;
- при изменении поведения обновляются связанные комментарии и документы в
  `docs`;
- пользовательские строки добавляются в `internal/i18n`, а не в UI напрямую;
- новые механики получают хотя бы один тест на обычный сценарий и один тест
  на отказ или крайний случай.
- UI-код документирует координатные зоны и публичные данные, которые он
  читает из игровой логики; UI не меняет приватное состояние юнитов напрямую.

## Правила очереди (назначение работы юнитам)

Слуги (`logistics`), фермер/пекарь (`villagers`) и лесоруб (`lumberjack`) —
три независимых контроллера, которые в рамках одного тика симуляции могут
претендовать на одни и те же ограниченные ресурсы (в первую очередь —
хлеб в харчевне). Это не полноценная FIFO-очередь ("Kafka на минималках"
не нужна для однопоточной симуляции в один процесс), а система
резервирования на основе `internal/reservations.Ledger`: общий реестр
"что уже кем-то занято в этом тике", который каждый контроллер сначала
заполняет своими текущими незавершёнными заявками (`Reserve`), а затем
читает при поиске новой работы (`Tick`). Правила:

1. **Резерв снимается сразу, как только ресурс физически забран.**
   Пока юнит идёт К точке забора, он резервирует её буфер. Как только груз
   у него в руках (в логистике — переход `toPickup -> toDropoff`), резерв
   источника снимается: буфер уже физически уменьшился, повторно вычитать
   его из реестра нельзя — иначе оставшееся на складе/ферме кажется
   меньше, чем есть на самом деле, до завершения доставки. Резерв точки
   назначения при этом держится всю поездку целиком (обе ноги пути), чтобы
   никто другой не попытался забить туда больше, чем есть места.

2. **Приоритет между тремя контроллерами — по времени ожидания голода, а
   не по порядку вызова в коде.** Перед тем как вызвать `Tick` у слуг,
   фермеров/пекарей и лесорубов, `cmd/game` спрашивает у каждого
   `MaxWaitingHunger()` — максимум тиков голода среди тех, кто прямо
   сейчас попробует пойти есть, — и тикает контроллеры в порядке убывания
   этого значения. Кто ждёт голодным дольше всех, тот и получает еду первым.

3. **Каждый источник/склад/харчевня проверяется на достижимость до того,
   как его принимают, а не после.** Поиск задания перебирает кандидатов
   через `pathfind`, пропуская недостижимых (отрезанная дорога и т.п.) и
   пробуя следующего, вместо того чтобы просто взять первого по порядку в
   списке зданий. Если в городе несколько харчевен или складов, выбирается
   ближайший **достижимый** — см. `nearestTavernWithBread`,
   `nearestReachableWarehouse` в `logistics`/`villagers`/`lumberjack`.

4. **Обход ресурсов в буфере — в фиксированном порядке, не через
   произвольный обход Go-map.** Итерация по `map[resource.Type]int`
   рандомизирована самим языком; там, где здание может одновременно
   держать несколько видов ресурса, порядок их рассмотрения фиксируется
   явной сортировкой (`sortedResourceTypes`), чтобы поведение не менялось
   от тика к тику без игровой причины.

Если что-то из этого меняется, комментарии над `assign`/`Reserve`/`Tick` в
каждом из трёх пакетов и этот раздел должны обновляться вместе.

## Проверка изменений

Перед передачей изменения нужно выполнить:

```text
go test ./...
go vet ./...
go build ./cmd/game
```

Если затронуты экономика, голод, дороги или слуги, первым запускается:

```text
go test ./internal/economy -run TestFullChain_FarmToMillToBakeryToTavern
```

## Сохранения

При несовместимом изменении `save.GameState` увеличивается `FormatVersion`,
а в `internal/save` добавляется тест на новый формат.
