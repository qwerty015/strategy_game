# AGENTS.md

Контекст для AI-агентов, работающих в этом репозитории.

## Язык общения

**Всё общение с пользователем — только на русском языке.** Пояснения, вопросы,
резюме — всё по-русски. **Текст внутри самой игры (HUD, подсказки, статусы,
заголовок окна) тоже должен быть на русском** — см. раздел "Локализация"
ниже, там это уже сделано через отдельный пакет `i18n`, а не хардкодом.
Код, комментарии в коде и имена пакетов/переменных могут оставаться на
английском, если так удобнее для самого кода.

## О проекте

Одиночная (без ИИ-противников, без боёв) градостроительная экономическая
игра: игрок строит здания, расширяет поселение и выстраивает цепочки
производства (поле → мельница → пекарня, виноградник → винодельня и т.д.),
с сохранением и загрузкой прогресса. Никакой ссылки на конкретную
существующую коммерческую игру в проектных материалах быть не должно —
описывать проект только в общих терминах жанра ("градостроительная
экономическая игра").

Логистика реализована по-настоящему (не абстрактно): здания должны быть
соединены дорогами со складом, и именно слуги физически переносят ресурсы
между зданиями и складом — см. "Логистика: дороги и слуги" ниже. Это
осознанный отход от изначального MVP-плана (там логистика была абстрактной
заглушкой) по прямому запросу пользователя — эта механика ключевая, не
опциональная полировка.

## Стек

- **Go + Ebitengine (ebiten v2).** Выбран вместо Python осознанно — чтобы
  из одной кодовой базы получить десктоп-бинарники, сборку под браузер
  (WASM) и в перспективе порт на Android (через `ebitenmobile`), без
  переписывания игровой логики.
- Пользователь — Python-разработчик с почти нулевым опытом в Go, этот
  проект для него — во многом ещё и способ выучить язык. Поэтому структура
  пакетов специально простая (без лишней вложенности), а горутины/каналы
  в игровой логике на старте не используются.

## Структура проекта

```
strategy_game/
  go.mod
  cmd/game/main.go        # точка входа: ebiten.RunGame, настройка окна
  internal/
    world/                 # Grid, Tile, типы рельефа
    building/               # Building, BuildingType, Recipe (данные, не код);
                             # Warehouse и Road — тоже Kind в этом же реестре
    resource/                # ResourceType, Stockpile (склад с лимитом) — это инвентарь Warehouse
    pathfind/                 # BFS по дорогам между зданиями
    logistics/                 # Serf, Controller — слуги, которые реально ходят и носят
    economy/                    # Simulator: тикает производство зданий (буферы), население ест хлеб
    i18n/                        # переводы (Catalog на язык), см. "Локализация"
    render/                       # камера, отрисовка тайлов/зданий/слуг
    ui/                            # палитра построек, панель ресурсов, курсор размещения
    save/                          # GameState, JSON-сохранение/загрузка
  assets/
    tiles/  buildings/  ui/
  saves/                    # файлы сохранений (slot1.json и т.д.)
```

Ключевые принципы архитектуры:

- **Рецепты производства — это данные, не код.** `building.Recipe{Inputs,
  Output, OutputAmount, TicksToProduce}`. Добавить новую цепочку (например,
  винодельню) — значит добавить новые значения `Recipe`, а не писать новую
  логику движка.
- **Игровая логика отделена от Ebiten.** Пакеты `economy`, `building`,
  `resource`, `pathfind`, `logistics`, `save`, `i18n` не импортируют ebiten
  — это чистый Go, тестируемый через `go test`, не требующий переписывания
  при сборке под WASM/Android. Ebiten трогают только `render`, `ui` и `cmd`.
- **Симуляция идёт по фиксированному тику** (`economy.Simulator.ShouldTick`),
  отдельно от кадров рендера, чтобы скорость производства не зависела от FPS.

## Логистика: дороги и слуги

- `Road` — это просто ещё один `building.Kind` (footprint 1×1, без рецепта).
  Переиспользует всю систему `CanPlace`/пересечений/сохранения бесплатно —
  отдельного поля/слоя для дорог в `world.Tile` нет и не нужно.
- `Warehouse` — единственный на карту, ставится автоматически в `NewGame`
  (координаты `warehouseX/warehouseY` в `cmd/game/main.go`), не через палитру
  игрока. Его инвентарь — это и есть общий `resource.Stockpile`.
- Обычные постройки (Farm/Mill/Bakery) **не трогают** общий Stockpile
  напрямую — только свои `InputBuffer`/`OutputBuffer` (см. `building.Building`,
  `BufferCapacity = 10`). Перекладывать ресурсы между буфером здания и
  складом — исключительно работа слуг.
- `pathfind.FindPath` — BFS: слуга может идти только по тайлам с `Road` и
  по footprint двух зданий-концов маршрута. Нет дороги — нет пути — здание
  не обслуживается (буфер просто копится/пустеет, лампочка прогресса стоит).
- `logistics.Controller` — вся модель через склад: либо "здание → склад"
  (Collect), либо "склад → здание" (Supply). **Нет прямой возки
  здание→здание** — это сознательное упрощение ради простого алгоритма
  назначения работы (полная задача о развозке — это отдельная, более
  сложная оптимизация; см. `assign`/`findCollectJob`/`findSupplyJob`).
- Состояние слуг (позиция, текущий груз/маршрут) **не сохраняется** в
  save-файл — при загрузке слуги просто заново создаются у склада
  (`logistics.NewController` вызывается заново в `handleSaveLoad`). Здания
  и их буферы, наоборот, сохраняются как есть (часть `building.Building`).

## Локализация

Все строки, которые видит игрок (HUD, подсказки, статусы, заголовок окна),
идут через пакет `i18n`, не хардкодом в `ui`/`cmd`:

- `i18n.Catalog` — набор полей на один язык; `i18n.T()` возвращает каталог
  активного языка, `i18n.SetLang(lang)` его переключает.
- Один язык — один файл (`ru.go`, `en.go`, ...), регистрирующий себя через
  `init()` → `register(lang, Catalog{...})`. Добавить новый язык — значит
  добавить один новый файл, не трогая остальной код.
- Активный язык сейчас жёстко задаётся в `main()` (`i18n.SetLang(i18n.RU)`
  — русский по умолчанию); выбора языка в самом UI игры пока нет, это
  следующий шаг, если понадобится.
- Внутренние идентификаторы (`resource.Type.String()`, ключи в JSON
  сохранений, `building.Type.Name`) намеренно остаются на английском для
  стабильности формата — локализуется только то, что реально выводится на
  экран.

## Сборка и запуск

```
go run ./cmd/game          # запуск с исходников
go build ./cmd/game        # десктоп-бинарник под текущую ОС
go test ./...              # юнит-тесты (economy/building/resource/pathfind/logistics/save)
```

Кросс-компиляция под другую ОС — через переменные `GOOS`/`GOARCH`. Сборка
под браузер — `GOOS=js GOARCH=wasm go build -o game.wasm ./cmd/game` плюс
`wasm_exec.js` от Ebiten и простая HTML-обёртка. Порт на Android —
отдельный будущий шаг через `ebitenmobile`, пока не начат.
