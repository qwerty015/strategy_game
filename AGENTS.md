Контекст для AI-агентов, работающих в этом репозитории.

## Язык общения

**Всё общение с пользователем — только на русском языке.** Пояснения, вопросы,
резюме — всё по-русски. **Текст внутри самой игры (HUD, подсказки, статусы,
заголовок окна) тоже должен быть на русском** — см. раздел "Локализация"
ниже, там это уже сделано через отдельный пакет `i18n`, а не хардкодом.
Код, комментарии в коде и имена пакетов/переменных могут оставаться на
английском, если так удобнее для самого кода.

## Не делай того, о чём явно не попросили

**Если пользователь задал вопрос — сначала ответь на вопрос.** Не начинай
менять код, не запускай эксперименты/симуляции в репозитории, не создавай
временные программы, пока пользователь явно не попросил что-то *сделать*.
Вопрос вида "сколько нужно X для Y, как думаешь?" — это вопрос, а не
задание разобраться любой ценой, включая правки файлов. Если для ответа
не хватает данных — либо дай оценку по уже известным числам/формулам в
коде, либо явно скажи, что для точного ответа нужно измерить, и спроси,
стоит ли это делать — но не делай этого молча.

## О проекте

Одиночная (без ИИ-противников, без боёв) градостроительная экономическая
игра: игрок строит здания, расширяет поселение и выстраивает цепочки
производства (поле → мельница → пекарня → харчевня, виноградник →
винодельня и т.д.), с сохранением и загрузкой прогресса. Никакой ссылки на
конкретную существующую коммерческую игру в проектных материалах быть не
должно — описывать проект только в общих терминах жанра
("градостроительная экономическая игра"), и не копировать её визуальный
стиль впритык, даже если пользователь присылает референс-скриншот именно
оттуда (см. "Графика" ниже — так уже было и решилось по-другому).

Логистика и труд реализованы по-настоящему (не абстрактно), по прямому и
подробному запросу пользователя, со ссылкой "как в оригинальной игре" —
это ключевые механики, не опциональная полировка:

- Здания должны быть соединены дорогами со складом/друг с другом, и именно
  слуги физически переносят ресурсы — см. "Логистика: дороги и слуги".
- Каждый юнит без исключения (слуга, фермер, пекарь, винодел, свиновод,
  мясник, лесоруб, рыбак) голодает по общей шкале сытости 0–100% и должен
  дойти до харчевни поесть; на нуле — умирает — см. "Голод, сытость и
  смерть".

**Важно:** заявлено "без ИИ-противников, без боёв" как принцип с самого
начала проекта. Пользователь уже предлагал добавить "соперника" —
компьютер, который просто строит свой посёлок по тем же правилам, без боя
(см. `docs/ROADMAP.md`, раздел "Соперник-строитель") — это пока
нереализованная идея, а не решение отказаться от принципа. Если берёшься
её реализовывать, сначала явно проговори с пользователем, что этот пункт
здесь обновляется — не делай это молча, между строк.

## Стек

- **Go + Ebitengine (ebiten v2).** Выбран вместо Python осознанно — чтобы
  из одной кодовой базы получить десктоп-бинарники, сборку под браузер
  (WASM) и в перспективе порт на Android (через `ebitenmobile`), без
  переписывания игровой логики.
- Пользователь — Python-разработчик с почти нулевым опытом в Go, этот
  проект для него — во многом ещё и способ выучить язык. Поэтому структура
  пакетов специально простая (без лишней вложенности), а горутины/каналы
  в игровой логике на старте не используются.

## Структура проекта

```
strategy_game/
  go.mod
  cmd/game/main.go        # точка входа: ebiten.RunGame, настройка окна, склейка всех контроллеров
  internal/
    world/                 # Grid, Tile, типы рельефа (в т.ч. Water)
    building/               # Building, BuildingType, Recipe (данные, не код);
                             # Warehouse, Road, Tavern, Tree, Fish — тоже Kind в этом же реестре
    resource/                # ResourceType, Stockpile (склад с лимитом) — это инвентарь Warehouse;
                              # FoodTypes()/IsFood() — какие ресурсы харчевня принимает как еду
    pathfind/                 # BFS по дорогам (FindPath), по любой суше (FindLandPath,
                               # для лесоруба), по воде (FindWaterPath, для рыбака)
    reservations/               # Ledger — общий "кто что уже занял в этом тике" реестр для
                                 # ВСЕХ контроллеров юнитов, см. "Логистика: дороги и слуги"
    meal/                        # Selector — детерминированный псевдослучайный выбор еды в
                                  # харчевне среди реально доступного на тик
    hunger/                       # общая шкала сытости 0–100% для всех живых юнитов, см.
                                   # "Голод, сытость и смерть"
    logistics/                     # Serf, Controller — слуги: носят грузы И сами едят
    villagers/                      # Villager, Controller — фермер/пекарь/винодел/свиновод/
                                     # мясник: работают дома, едят в харчевне
    lumberjack/                      # Lumberjack, Controller — лесорубы и добыча брёвен
    fishing/                          # Fisherman, Controller — рыбаки, лодка, рыба в воде
    economy/                           # Simulator: тикает производство зданий (буферы)
    i18n/                               # переводы (Catalog на язык), см. "Локализация"
    assets/                              # эмбеднутые PNG-спрайты (go:embed), см. "Графика"
    render/                              # камера, отрисовка тайлов/зданий/юнитов
    ui/                                  # палитра построек, найм, HUD, инспектор, текст
    save/                                # GameState, JSON-сохранение/загрузка, миграция версий
  saves/                    # файлы сохранений: slot1.json (S/L) + panel_slot_1..5.json (боковая панель)
```

Ключевые принципы архитектуры:

- **Рецепты производства — это данные, не код.** `building.Recipe{Inputs,
  Output, OutputAmount, TicksToProduce}`. Добавить новую цепочку — значит
  добавить новые значения `Recipe` и, если у здания появляется свой
  рабочий, новую `Profession` — а не писать новую логику движка. Уже так
  добавлены винодельня, свиноферма+мясной цех, рыбак, столярная
  мастерская (`resource.Plank`, профессия `villagers.Carpenter`) и
  каменоломня (`resource.StoneBlock`, пакет `quarry`). Ни одна из этих
  цепочек не потребовала менять `economy` или
  `internal/reservations`; у столярки, каменоломни и обоих работников есть
  собственные спрайты из `internal/assets/generated`.
- **Игровая логика отделена от Ebiten.** Пакеты `economy`, `building`,
  `resource`, `pathfind`, `logistics`, `villagers`, `lumberjack`, `fishing`,
  `reservations`, `meal`, `hunger`, `save`, `i18n` не импортируют ebiten —
  это чистый Go, тестируемый через `go test`, не требующий переписывания
  при сборке под WASM/Android. Ebiten трогают только `render`, `ui` и `cmd`.
- **Симуляция идёт по фиксированному тику** (`economy.Simulator.ShouldTick`),
  отдельно от кадров рендера, чтобы скорость производства не зависела от FPS.
- Полный сквозной путь (Farm → Mill → Bakery → Tavern, включая голод
  фермера/пекаря) покрыт интеграционным тестом:
  `internal/economy/integration_test.go`. Если трогаешь логистику,
  экономику или голод — прогони именно его первым, он ловит дедлоки между
  подсистемами, которые юнит-тесты отдельных пакетов не видят (см. ниже
  про реальный такой дедлок).

## Логистика: дороги и слуги

- `Road` — это просто ещё один `building.Kind` (footprint 1×1, без рецепта).
  Переиспользует всю систему `CanPlace`/пересечений/сохранения бесплатно —
  отдельного поля/слоя для дорог в `world.Tile` нет и не нужно.
- `Warehouse` — первый склад ставится автоматически в `NewGame`, дополнительные
  склады можно ставить в палитре и удалять (`logistics.RemoveWarehouse`;
  последний склад защищён). Все склады используют общий безлимитный
  `resource.Stockpile`; если удаляемый склад был основным, точкой найма
  становится другой. Когда складов/харчевен несколько, юнит всегда выбирает
  **ближайший достижимый**, а не первый по порядку (`nearestReachableWarehouse`,
  `nearestTavernWithFood` в каждом из пакетов юнитов) — это была реальная
  регрессия ("слуги носят только в один склад"), исправленная явной сортировкой
  по длине пути, не полагаясь на порядок в срезе `buildings`.
- `LumberjackHut`/`FisherHut` — рабочие здания без обычного рецепта: их
  работник (лесоруб — `pathfind.FindLandPath`, любая суша и дороги, кроме
  воды/зданий/деревьев; рыбак — `pathfind.FindPath` по суше и
  `pathfind.FindWaterPath` по воде на лодке) физически добывает ресурс и
  кладёт его в буфер хижины, откуда уже обычный слуга забирает его по дороге.
- Обычные постройки **не трогают** общий Stockpile напрямую — только свои
  `InputBuffer`/`OutputBuffer` (`BufferCapacity = 6` — лимит на любой ресурс
  в любом здании, кроме склада).
- `pathfind.FindPath` — BFS: слуга может идти только по тайлам с `Road` и
  по footprint двух зданий-концов маршрута — **не через footprint третьего,
  случайно стоящего на пути здания**. Значит: если здания просто выстроить
  в ряд впритык к дороге, дорога должна идти *мимо* них (соседним рядом
  тайлов), а не через их клетки — иначе один дом блокирует путь между двумя
  другими. Смотри разводку дорог в
  `internal/economy/integration_test.go` как пример правильной раскладки
  (через-дорога отдельно, здания примыкают к ней сбоку).

### Реестр резервирования (`internal/reservations`) — не Kafka, а честный учёт

Изначальная проблема пользователя: "толпа слуг идёт за одним и тем же
заданием" — несколько простаивающих юнитов независимо "видят" одну и ту же
ограниченную партию ресурса и все берутся её везти. Решение — **не**
message queue, а `reservations.Ledger`: общий, каждый тик пересобираемый с
нуля реестр "что уже кем-то занято прямо сейчас". Каждый из четырёх
контроллеров юнитов (`logistics`, `villagers`, `lumberjack`, `fishing`)
сначала вызывает `Reserve(ledger)` (регистрирует уже занятые в пути грузы),
затем `Tick(..., ledger)` (ищет новую работу, читая доступность через
`ledger.AvailableOutput`/`AvailableInput`/`AvailableStock`, а не сырые
буферы). В `cmd/game.Update` все четыре вызова идут на одном общем
`ledger`, и порядок тиков контроллеров **не фиксирован**: он каждый раз
пересчитывается по `MaxWaitingHunger()` каждого контроллера — у кого
голоднее всех юнит, тот тикает первым, иначе слуги систематически ели бы
раньше фермеров просто потому, что стоят раньше в коде. Полные правила — в
`docs/DEVELOPMENT.md`, раздел "Правила очереди"; их девять, включая
обязательные для поиска задания второе плечо маршрута (источник должен уметь
физически довезти груз получателю, не только юнит доехать до источника) и
детерминированный (сортированный) обход ресурсов здания вместо обхода
Go-map.

### Приоритет снабжения (`logistics.Controller.SetPriority`)

Игрок может назначить приоритет **виду** здания (не экземпляру) — слайдер в
инспекторе выбранного здания, 5 уровней. Приоритет ломает равенство внутри
уже существующих уровней очереди (`findDirectJob`/`findCollectJob`/
`findSupplyJob`), когда несколько *разных видов* потребителей одновременно
претендуют на общий ограниченный ресурс — например, Мельница и Свиноферма
обе за Пшеницу. Харчевню и сами уровни очереди приоритет не переставляет —
это осознанное ограничение по прямому запросу пользователя. Хранится в
`save.BuildingPriority`, показывается только для зданий с непустым
`Recipe.Inputs` (`priorityEligible` в `cmd/game`).

Список слуг/фермеров/лесорубов/рыбаков, их позиции, сытость и статус голода
сохраняются в `save`-файл. Незавершённый маршрут после загрузки не
сериализуется: новый маршрут строится от сохранённой клетки, поэтому юнит не
телепортируется обратно на склад/домой. Здания и их буферы также
сохраняются как есть.

## Голод, сытость и смерть

Пользователь явно попросил "как в оригинальной игре": **каждый** юнит без
исключения (слуга, фермер, пекарь, винодел, свиновод, мясник, лесоруб,
рыбак, каменотёс, строитель, рудокоп, плавильщик) голодает и должен дойти
до `Tavern` (харчевня) поесть, а не
абстрактное "население" ест хлеб со склада само по себе. Позже это
расширили до полноценной шкалы: сытость 0–100%, поход в харчевню при 20%,
**смерть при 0%** — тоже для всех без исключения.

- `internal/hunger` — единственный источник правды по тайминг-константам:
  `MaxTicks = 1300` (полный запас, ~10 мин 50 с на обычной скорости — 1%
  уходит за 13 тиков; на 30% больше исходных 1000/~8 мин 20 с — по прямому
  запросу пользователя "юниты жили дольше"), `MealThresholdTicks = 1040`
  (по-прежнему ровно 80% от `MaxTicks`, 20% — порог похода поесть).
  `Percent(elapsed)` вычисляет через `MaxTicks` напрямую
  (`100 - elapsed*100/MaxTicks`), а не через захардкоженный делитель — при
  следующей перебалансировке этого таймера значения 0-100% не разъедутся
  сами собой. `Percent(elapsed)`, `NeedsMeal(elapsed)`, `Dead(elapsed)` —
  три чистые функции, ими пользуются все семь пакетов юнитов (слуга,
  villagers, лесоруб, рыбак, каменотёс, строитель, рудокоп), чтобы
  тайминги не расходились по мере добавления профессий.
- `building.Tavern` хранит еду в своём `InputBuffer`. Еды сейчас четыре
  вида — Bread, Fish, Wine, Sausage (`resource.FoodTypes()`), все
  равноценны: голодный юнит ищет **ближайшую достижимую** харчевню с хоть
  какой-то едой (`nearestTavernWithFood` в каждом из четырёх пакетов
  юнитов — не просто первую в списке зданий, это тоже была реальная
  регрессия), а какую конкретно еду съесть — определяет `internal/meal`
  (детерминированный псевдослучайный выбор среди реально доступного на
  этот тик, зерно сохраняется в файл, чтобы результат был воспроизводим
  после загрузки).
- У каждого юнита свой `Tick`, но общая форма: `ticksSinceMeal`/`hungerTick`
  растёт **не ограниченно** каждый тик (важно — раньше был баг, когда
  счётчик капался на пороге похода поесть; это ломало сортировку по
  голоду ниже, см. doc-комментарий `MaxWaitingHunger` в каждом пакете).
  `SatietyPercent()`/`HungerTicks()` — паблик-геттеры для UI.
- Если юнит достиг `hunger.Dead`, контроллер удаляет его из своего списка
  на этом же тике (роняет любой переносимый груз обратно в общий запас,
  если нёс) и сообщает об этом наружу (`logistics.TickResult.Deaths`,
  `villagers.Controller.Tick` возвращает `int`, `lumberjack`/`fishing`
  отдают `Event{Kind: WorkerDied}`). `cmd/game` суммирует это в
  `Population.Deaths` для шапки.
- **Реальный баг, который тут был:** контроллеры `lumberjack`/`fishing`
  фильтруют список юнитов "на месте" через паттерн `remaining :=
  c.Xxx[:0]` + `append` в конце тела цикла. Но их `switch` по состоянию
  почти на каждой ветке делает `continue` ("ещё иду", "ещё рублю") — это
  пропускало `append` и **удаляло живого юнита из ростера уже на первом
  тике**. Чинится вызовом `append` сразу после проверки на смерть, до
  `switch`, а не после него. Если добавляешь новый такой контроллер —
  сразу пиши `append` в начале тела цикла, не в конце.
- `Villager.Starving` / `Serf.Starving` / `Lumberjack.Starving` /
  `Fisherman.Starving` — true, когда юнит голоден, но реально не может
  дойти поесть (харчевни ещё нет, дорога не проложена, или еды нигде нет).
  Это **только статус** (для красного оттенка в рендере) — не блокирует
  работу. См. следующий пункт, почему.
- **Реальный дедлок, который тут был и словился интеграционным тестом:**
  если гасить производство здания по `Villager.Starving` (а не по
  `!Villager.Working()`), первый цикл свежего города заходит в тупик —
  харчевня не может получить хлеб, пока пекарня не испечёт хоть одну
  партию, а пекарня "голодает" и не работает, пока в харчевне нет хлеба.
  Правильно (см. `Game.inactiveWorkerBuildings` в `cmd/game/main.go` и
  идентичный хелпер в интеграционном тесте): гасить производство **только**
  когда работник физически отсутствует (`!v.Working()` — ушёл есть или
  идёт обратно), а не просто голоден-но-на-месте. Если снова трогаешь эту
  логику — не путай два условия обратно, тест это словит, но дешевле не
  наступать заново. `Game.unstaffedWorkerBuildings` — отдельный, более
  строгий хелпер только для красной подсветки на карте: здание без
  назначенного работника вообще (в отличие от "отошёл поесть").
- `economy.Population` теперь — счётчик для HUD ("Население: N", плюс
  `Deaths`/`Removed`), не самостоятельная симуляция: `cmd/game` каждый тик
  пересчитывает `pop.Count` по факту живых юнитов
  (`Game.refreshPopulation`). `economy.Tick` не принимает ни `*Population`,
  ни `*Stockpile` — только `inactive`/`disconnected map`.
- Фермеры, пекари, виноделы, свиноводы, мясники, плавильщики, лесорубы,
  рыбаки, каменотёсы, рудокопы и строители сохраняются вместе с профессией, позицией,
  рабочим зданием (у строителя — склад, к которому он приписан, не хижина),
  сытостью и состоянием похода в харчевню. После загрузки их дорожный маршрут
  восстанавливается от сохранённой клетки; старые сохранения без списка юнитов
  загружаются с прежним стартовым составом.

## Голод: два реальных бага дистанции/ожидания

Пользователь сообщил, что строители умирают, ожидая ресурсы, а
рудокоп/каменотёс/лесоруб — от больших расстояний ("не успевает дойти
чтобы покушать"). Расследование вскрыло **два разных бага**, оба
существовали и раньше, но были почти незаметны на маленькой карте 40×30 и
стали смертельны только на большой 100×75 (тот же класс проблемы, что и
CPU-баг с картой — маленькая карта прятала баг, большая его вскрыла):

- **Бесконечное ожидание без проверки голода.** Голод проверяется только
  в `StateIdle` (везде, во всех семи пакетах юнитов) — но у нескольких
  профессий есть состояние ожидания внешнего события **без верхней
  границы по времени**, которое никогда не возвращается в `StateIdle`,
  пока событие не случится: `builder.StateWaitingMaterials` (ждёт, пока
  слуга довезёт доски/камень — может не дойти очень долго, если стройка
  далеко или материалов не хватает) и `StateUnloading` у
  lumberjack/quarry/miner (ждёт, пока слуга заберёт полный буфер хижины —
  может не прийти долго при перегруженной логистике). `hunger.Dead`
  проверяется безусловно в начале `Tick` независимо от состояния — значит
  юнит в таком "залипшем" ожидании гарантированно умирал, даже стоя в
  двух шагах от полной харчевни, потому что код ожидания просто крутил
  `continue` вечно, ни разу не заглядывая в `hungerTick`.
  **Исправлено** добавлением проверки голода прямо в эти состояния,
  вызывающей тот же `tryStartMeal`, что и `StateIdle`:
  - `builder`: `b.target` (стройплощадка) не трогается `tryStartMeal`, но
    штатный постобеденный переход в `StateToTavern` раньше **всегда**
    уходил в `resetToIdle()` (который стирает `target`) — так что просто
    добавить проверку голода было недостаточно: `startSiteJob` из
    `StateIdle` не знает, что площадка уже прошла фазу фундамента, и
    начал бы её заново. Постобеденный переход теперь проверяет
    `b.target.ConstructionStage == ConstructionWaitingMaterials` и
    возвращает строителя обратно в `StateWaitingMaterials` на ту же
    площадку, а не в `StateIdle`.
  - `lumberjack`/`quarry`/`miner`: тут проще — `cargo` не трогается
    `tryStartMeal` и переживает `resetToIdle` (не в списке полей, которые
    он чистит), а `StateIdle` уже (у lumberjack/quarry) имел ветку
    `if cargo > 0 { routeHome(); continue }` **раньше** проверки голода —
    так что после еды груз сам находит дорогу обратно. У **miner** такой
    ветки не было вообще (не было нужды — `StateUnloading` раньше не
    отпускал майнера с грузом никуда) — пришлось добавить её тоже,
    иначе `startDepositJob` начал бы новую добычу поверх ещё не сданного
    груза и тихо его потерял бы при следующей разгрузке.
- **Нет проверки голода посреди дороги.** `StateToTree`/`StateChopping`/
  `StateToHome` (и деposit-аналоги у quarry/miner) тоже никогда не
  проверяют голод — если путь туда-обратно физически длиннее оставшегося
  запаса сытости, юнит умирает прямо на дороге, и это не лечится
  предыдущим пунктом (тот чинит только "залипание", а не "слишком долгий,
  но конечный путь"). Вместо перехвата на середине пути (сложнее: нужно
  бросать недоделанную работу) — **`lumberjack.MaxWorkRadius` /
  `quarry.MaxWorkRadius` / `miner.MaxWorkRadius` (45 клеток пути, не по
  прямой)** в `startTreeJob`/`startDepositJob`: цель дальше этого просто
  никогда не выбирается, даже если это единственная доступная. Число
  выведено из бюджета голода: `StateIdle` уже не пускает юнита в новую
  работу, если `hungerTick >= HungerInterval`, так что худший случай —
  начать путь прямо перед порогом, оставляя
  `hunger.MaxTicks - HungerInterval` (~260 тиков) на весь обратный путь;
  при `TicksPerTile=2` это округляется до ~62 клеток пути в один конец
  для полного цикла туда-обратно+работа — 45 оставляет заметный запас.
  **`builder.startSiteJob` сознательно не получил такое же ограничение** —
  см. развёрнутый doc-комментарий на самой функции: стройплощадка
  уникальна (не взаимозаменяема, как дерево/руда), пропуск дальней
  оставил бы её навсегда недостроенной, а не отправил строителя к
  ближайшей замене; без верхней границы это и не нужно — тот же бюджет
  голода даёт ~130 клеток запаса на **один** длинный переход (в отличие от
  туда-обратно), с запасом покрывающих всю карту, а `StateWaitingMaterials`
  на месте уже не смертелен после фикса выше.
- **Локальный повторный засев рыбы/деревьев рядом с местом сбора** —
  реализовано отдельно, см. "Локальность возрождения рыбы и деревьев"
  ниже (была часть этого же обсуждения, но отдельная от голода проблема).
- **Ещё не сделано, но обсуждалось с пользователем как следующие шаги** (не
  реализовано в этом заходе, см. историю сессии): скопление ресурсов в
  несколько кластеров ближе к старту вместо равномерного разброса минимум
  в `minDepositDistanceFromWarehouse` клетках; диагональное
  движение (8 направлений вместо 4 в `pathfind.neighbors`, вдвое короче
  путь по диагонали) — крупная, отдельная переделка, трогающая тайминг
  всех профессий разом; "grace-период" — предложенная пользователем
  альтернатива текущему фиксу (после ~30% сытости голод течёт медленнее,
  юнит физически медленнее) — не реализована, поскольку `MaxWorkRadius`
  уже структурно исключает сам сценарий "не успел дойти".

## Локальность возрождения рыбы и деревьев

Пользователь сообщил (и подтвердил на сохранении): рыбак вычищает рыбу
рядом со складом, дальние рубежи не трогает, но рыба **возрождалась**
где угодно на всём водоёме случайно — со временем вся рыба оказывалась
далеко, а около респы пусто. Та же картина с деревьями: рядом с респой
вырубают, регенерация была не привязана к месту вырубки, и дальние
"чащи" со временем становились фактически недостижимым лесом
(`MaxWorkRadius`, см. выше, не даёт лесорубу даже попытаться туда
дойти). Причина — старые `tickTreeRegrowth`/`tickFishRegrowth` выбирали
новое место **по всей карте/всему водоёму** и проверяли **глобальный**
потолок численности (`maxTrees := grid.Width*grid.Height/100`,
`fishBodyLimit` на весь `waterBodyCells`) — не важно, где именно что-то
собрали, лишь бы общее число не превышало лимит. Результат: сбор в одном
месте и рост в другом медленно перекачивал весь ресурс на нетронутый
край карты.

**Исправлено** заменой (не добавлением поверх) глобального критерия на
**локальный, привязанный к месту сбора**:

- `treeRegrowth` теперь хранит `originX/originY` — где именно спилили
  дерево, освободившее слот на возрождение (`cutTree` передаёт
  `tree.X, tree.Y` в `scheduleTreeRegrowth`, `save.TreeRegrowthState`
  хранит `OriginX/OriginY`; 0,0 в старом сохранении безвредно — просто
  ещё одна точка отсчёта, зона переприкинется на следующей неудачной
  попытке). `tickTreeRegrowth` считает деревья **только в радиусе**
  `treeRegrowthRadius = 20` от `origin` (`countTreesNear`, замена
  убранной `countTrees`) и ищет свободную клетку **тем же радиусом**
  (`findTreeSpawnCell(seed, origin, radius)` — сузил область поиска
  вместо скана всей карты), не глобально; локальный потолок —
  `treeRegrowthLocalCap = 12` (на радиус 20, не на всю карту).
- Для рыбы — то же самое, но по воде: новая `waterSectionCells(grid,
  start, radius)` — BFS по воде, обрезанный по числу шагов
  `fishRegrowthRadius = 20` (в отличие от неограниченного
  `waterBodyCells`, который остался как есть и по-прежнему используется
  при генерации мира в `seedFish` — там локальность не нужна, это
  разовый посев). `tickFishRegrowth` теперь зовёт
  `waterSectionCells(grid, {regrowth.waterX, regrowth.waterY},
  fishRegrowthRadius)` вместо `waterBodyCells`; `fishRegrowth.waterX/Y`
  уже хранил точное место поимки, новых полей не понадобилось —
  `fishBodyLimit`/`countFishInCells`/`findFishSpawnCell` не менялись,
  просто теперь работают на обрезанном множестве клеток.

Итог: и рыба, и дерево возрождаются в том же районе, где их собрали, а
не на другом конце карты/водоёма — вычищенная зона со временем
восстанавливается сама, а не остаётся пустой навсегда, пока весь ресурс
скапливается там, куда никто не доходит.

## Каменоломня и конечные ресурсы

Камень — первый **конечный** ресурс в игре: в отличие от дерева/рыбы, у
месторождения нет очереди на восстановление. Архитектурно это решено почти
целиком переиспользованием паттерна Tree/Lumberjack, с несколькими
намеренными отличиями:

- **Месторождение (`building.StoneDeposit`) — обычный объект в
  `buildings`, а не тайл рельефа.** Была соблазнительная альтернатива —
  использовать уже существующий (но никогда не подключённый к геймплею)
  `world.TerrainType.Stone` и `Tile.Buildable()`, но это ломает
  проходимость: `pathfind.landWalkable` проверяет `tile.Buildable()`
  **до** исключения для стартовой/целевой клетки, так что каменотёс не
  смог бы даже дойти до месторождения на нехождённой террейн-клетке.
  Building-объект работает бесплатно: `footprintsOverlap` уже блокирует
  стройку поверх него (как поверх дерева), а `p == start || p == goal` в
  `landWalkable` уже разрешает дойти до самой клетки, не проходя её как
  промежуточную — тот же трюк, что и с деревом;
- **`Building.Reserve int`** — новое поле, генерическое (не только для
  камня, задумано и для будущих руд из ROADMAP). Стартует с
  `building.StoneDepositReserve` (10000), уменьшается на 1 за проход
  добычи; объект убирается из мира только когда дошёл до 0 — в отличие от
  дерева (которое убирается сразу после одной рубки), одно месторождение
  переживает тысячи проходов;
- **Никакого резервирования цели, в отличие от дерева.** `lumberjack`
  не даёт двум лесорубам рубить одно дерево одновременно
  (`treeReserved`) — там смысл: дерево даёт ровно одно бревно и исчезает.
  Для месторождения с запасом 10000 это ограничение не нужно и было бы
  чистым вредом: несколько каменотёсов (в т.ч. из разных Каменоломен)
  намеренно могут добывать в одном месторождении одновременно
  (`internal/quarry`, `startDepositJob` не проверяет занятость цели);
- **Переработка встроена в добычу, отдельного здания не нужно.**
  `Quarryman.Cargo()` уже возвращает удвоенное значение (2 каменных блока
  на 1 добытую единицу) — камень как отдельный `resource.Type` вообще не
  существует, есть только внутреннее поле `cargo` (0 или 1) и публичный
  `resource.StoneBlock`. Раздельный `RawCargo()` существует специально для
  сохранения/восстановления: `Restore` реконструирует внутреннее
  доконверсионное поле, и если бы туда попало уже удвоенное значение из
  `Cargo()`, следующая разгрузка задвоила бы конверсию;
- **`save.GameState.StoneSeeded`** — обязательный явный флаг, потому что у
  месторождений (в отличие от деревьев/рыбы) нет очереди восстановления,
  по длине которой можно было бы отличить "старое сохранение без этой
  механики" от "все месторождения честно выработаны". `false` в старом
  сохранении включает миграцию (`ensureStoneDeposits` генерирует регион),
  `true` — не трогает мир, даже если живых месторождений уже 0;
- **Генерация — 2-5 отдельных областей, не единый разброс, как у
  деревьев.** `seedStoneDeposits` делит случайные 5-10% площади карты между
  2-5 регионами и растит каждый BFS-подобным "blob"-алгоритмом
  (`growStoneRegion`) от одной стартовой точки, а не разбрасывает
  отдельные клетки по всей карте, как `seedTrees`. Пользователь прямо
  попросил "разные части карты" вместо одной области;
- **Реальный баг рендера, который тут был:** `StoneDeposit` сначала рисовался
  в общем цикле `DrawBuildings` вперемешку со стоящими зданиями — и клетка
  месторождения, оказавшаяся в слайсе `buildings` позже соседнего высокого
  здания (`buildingHeight = 1.7`, спрайт "нависает" над своей клеткой),
  рисовалась поверх его нижней части. Починено переносом отрисовки
  месторождения в тот же самый первый проход, что и у дорог (плоский
  грунтовый слой, всегда снизу) — см. doc-комментарий в
  `render.DrawBuildings`. Если добавляешь ещё один плоский "ground-level"
  объект (руда, декорация) — он тоже должен рисоваться в этом первом
  проходе, а не в основном цикле по стоящим зданиям.

## Стройка: ресурсы, строитель, доставка не по дороге

Постройка (кроме стартовых склада и дороги из `NewGame`) больше не
появляется готовой мгновенно. Архитектура:

- **`building.ConstructionStage`** живёт прямо на `Building`
  (`ConstructionNone`/`Foundation`/`WaitingMaterials`/`Finishing`), как
  `GrowthTicks` у дерева. Zero-value — `ConstructionNone`, то есть уже
  готово: любое здание из старого сохранения или из `NewGame`
  автоматически считается достроенным, миграция не нужна.
  `building.NewConstructionSite(kind, x, y)` — то, что теперь создаёт клик
  по палитре, вместо мгновенно готового `&Building{Kind: kind, ...}`.
  `ProgressTicks` (то же поле, что у обычного рецепта) переиспользуется как
  счётчик тиков **внутри текущей стадии** — недостроенное здание не может
  одновременно быть недостроенным и производить, так что конфликта с
  обычным `economy.TickWithConnectivity` нет: та функция первым делом
  пропускает любое здание с `ConstructionStage != ConstructionNone`.
- **Два этапа, не один рецепт.** Фундамент (`Type.ConstructionFoundationTicks`)
  строитель копает бесплатно, материалы не нужны совсем — пользователь
  прямо попросил именно так, а не "рецепт без прогресса без материалов",
  как у обычных зданий. Как только фундамент готов,
  `Building.ConstructionMaterialsReady()` решает: если доски/камень уже
  привезли — сразу в `Finishing`, если нет — в `WaitingMaterials` и ждать.
  `Type.PlankCost`/`StoneCost` — сколько нужно всего. По прямой просьбе
  пользователя ("снизим стоимость зданий") стоимость **плоская для всех
  зданий — 5 досок + 5 каменных блоков**, включая то, что раньше стоило
  дороже (винодельня/свиноферма/хижина рыбака были 15 досок за
  забор/лодку — `fencedPlankCost` убран совсем, отдельного тарифа больше
  нет). **Дорога — намеренное исключение**, подтверждённое пользователем
  явно ("дорога 1 клетка 1 камень, старая цена"): 1 камень за клетку без
  досок вовсе, не тронута.
  `Building.AddConstructionMaterial` кладёт в `InputBuffer`, но капается не
  обычным `BufferCapacity` (6), а именно этой стройко-стоимостью — сейчас
  она меньше (5), но принцип не завязан на конкретное число: механизм
  переживёт следующее изменение баланса без правки кода.
- **`internal/builder`** — контроллер строителей, по образцу
  `lumberjack`/`quarry` (`pathfind.FindLandPath`, любая суша, не только
  дороги — пользователь прямо это попросил), но **без своего здания**:
  `Builder.Warehouse` — просто точка спавна найма
  (`builder.Controller.Hire(warehouse)`), не "дом", в который прячешься
  при простое. `VisibleOnMap()` у строителя всегда `true` и `resetToIdle`
  никуда не телепортирует — он просто стоит там, где закончил последнее
  задание, точно как слуга после `Serf.reset()` (первая версия копировала
  lumberjack'овский "иди домой поесть, потом иди домой снова" — оказалось
  лишним усложнением без хижины, которая оправдывала бы это у лесоруба).
  Один строитель на объект — `siteReserved`, как `treeReserved` у
  лесоруба (в отличие от месторождения камня, где несколько каменотёсов
  специально разрешены).
- **Найм строителя — единственное исключение из "лимит по числу
  зданий".** У строителя нет здания, которое считало бы лимит, поэтому
  `cmd/game`'s `maxBuilders = 3` — простой фиксированный потолок, а не
  `countBuildings(...)`-подсчёт, как у всех остальных профессий.
  `finishConstruction` (реакция на `builder.ConstructionComplete`) —
  единственное место, где (для склада) `logi.AddWarehouse` теперь
  вызывается: раньше это происходило сразу при клике по палитре, теперь —
  только когда здание реально достроено, иначе недостроенный склад начал
  бы принимать грузы. `finishConstruction` **не** зовёт `spawnWorkersFor` —
  по прямому запросу пользователя достроенное здание не получает жителя
  само, см. "Золото и наём" ниже.
- **Единственная доставка слуги не по дороге.** Обычные грузы всегда идут
  через `pathfind.FindPath` (нужна дорога) — это не меняется. Но доски и
  камень для стройки — намеренное исключение:
  `logistics.findConstructionSupplyJob` +
  `nearestReachableWarehouseOverLand` +
  `Serf.construction`-флаг заставляют это ОДНО плечо маршрута ходить через
  `pathfind.FindLandPath`. Причина — не удобство, а бутстрап: без этого
  самую первую дорогу в городе было бы физически невозможно построить,
  потому что для доставки на неё камня по правилам понадобилась бы уже
  готовая дорога. Реестр резервирования это исключение не ломает:
  `ledger.RoomFor(site, resource.Plank, site.ConstructionMaterialCost(Plank))`
  — тот же механизм, что и у обычных потребителей, только `target` берётся
  из стройко-стоимости, а не из `Recipe.Inputs`.
- **Дорога сама по себе тоже стройка.** `Road` — тот же `Building`
  (см. раздел "Логистика" выше), так что `pathfind.roadSet` теперь
  явно проверяет `ConstructionStage == ConstructionNone` — недостроенная
  дорога не может быть частью маршрута ни для слуги, ни для
  "требуется хотя бы одна дорога в пути" (`containsRoad`). Если добавляешь
  ещё одну проверку "это дорога" где-то ещё — не забудь про этот флаг.
- **Отмена (Delete) недостроенного здания.** В отличие от дерева/рыбы/
  месторождения (их удалить нельзя вообще), недостроенное здание
  удаляется как обычно, но с отдельной веткой в начале
  `deleteSelectedBuilding`: уже привезённые доски/камень возвращаются на
  склад, `builders.CancelRouteTo` освобождает строителя, а проверка "нельзя
  удалить последний склад" не применяется вовсе — недостроенный склад
  никогда не регистрировался как логистическая точка (см. выше), так что
  удалять его как склад не нужно.
- **Рендер — намеренно условный: нет отдельного арта на 13 видов
  строек.** `render.drawConstructionSite` рисует одну и ту же
  полупрозрачную плашку (цвет древесины) с обычным жёлтым прогресс-баром
  (`Building.ConstructionProgress()`, 0..1 по обеим стадиям сразу) поверх
  footprint любого вида здания; на `ConstructionWaitingMaterials` плашка
  краснеет — тот же язык "требует внимания", что у `unstaffedTint`.
  Недостроенная дорога рисуется тем же плейсхолдером в том самом первом
  (грунтовом) проходе, что и обычная дорога/месторождение камня — иначе
  она бы либо не отрисовалась вообще, либо намалевалась поверх соседних
  зданий той же порядковой проблемой, что была с месторождениями камня
  (см. выше).

### Реальный баг: слуги ходят по кругу, доставка стройки зависает навсегда

Пользователь заметил в сохранении застрявший склад под стройкой (у самой
воды): прогресс-бар не заполняется, при этом по ощущению туда уже
отнесли нереальное количество материалов, а строитель рядом почти умирал
от голода (`HungerTicks` близко к `hunger.MaxTicks`) — и прямым текстом
описал причину: "слуги ходили по кругу с материалами между складом и
строящимся складом... материалы на стройку не доставились".

Причина — отсутствие повторной проверки маршрута после того, как задание
уже выдано. `nearestReachableWarehouseOverLand` проверяет, что путь до
площадки существует, **в момент назначения задания**. Пока слуга идёт до
склада за грузом, на карте могло появиться новое здание, перекрывшее тот
самый (единственный) путь — `arriveAtPickup` честно перепроверяет маршрут
второй раз перед выходом со склада и, если его больше нет, возвращает
груз и уходит в простой. Но ничто не мешало **следующему** освободившемуся
слуге (или тому же самому на следующем тике) тут же снова найти ровно то
же самое задание — `findConstructionSupplyJob`/`findConstructionDirectJob`
не помнят о недавнем провале — и повторить тот же провальный цикл: идти
на склад, забрать груз, дойти, не найти путь, вернуть груз, повторить.
Стройка при этом реально не продвигается ни на шаг, хотя со стороны
выглядит как непрерывная бурная логистическая активность.

**Исправлено** коротким троттлингом на стороне площадки, а не задания:
`logistics.Controller.constructionBackoff map[*building.Building]int` —
таймер отката (`constructionBackoffTicks = 120` тиков), выставляемый в
`arriveAtPickup` ровно в момент, когда повторная проверка маршрута
проваливается (`s.construction && s.dropoff != nil`, перед `s.reset()`).
`findConstructionSupplyJob`/`findConstructionDirectJob` получили новый
параметр `blocked map[*building.Building]int` и пропускают
(`continue`) любую площадку с `blocked[cand] > 0` — та же карта, что и
`constructionBackoff`, передаётся из `assign()`. Обратный отсчёт —
`Controller.tickConstructionBackoff()`, вызывается первым делом в
`Tick()`, до цикла по слугам; запись удаляется по достижении нуля, и
площадка снова становится обычным кандидатом. Карта **не сохраняется** в
файл сохранения — это временный троттлинг, а не игровое состояние: после
загрузки сохранения площадка просто получает один шанс попробовать
снова, прежде чем откатиться опять, если маршрут всё ещё перекрыт.
`NewController` — единственное место, где создаётся `Controller` (в коде
нет ни одного "сырого" литерала `&Controller{...}` в обход неё), так что
карта гарантированно инициализирована.

## Уголь, руда и Плавильня

По прямому запросу пользователя ("добываем руду (золото, железо) и
отдельно уголь... руда переплавляется в ресурс: золото или железо, уголь
используется для переработки... угля должно быть больше... нужна
очередь... может плавильню одну и исходя из того что сейчас плавится то и
получается на выходе?"). Архитектурно — почти целиком переиспользование
Каменоломни/StoneDeposit, плюс два новых, первых-в-проекте паттерна:

- **`building.NewOreDeposit(kind, x, y)`** обобщает `NewStoneDeposit` на
  три вида (`CoalDeposit`/`GoldOreDeposit`/`IronOreDeposit`), тот же
  `Building.Reserve`, но свой лимит `OreDepositReserve` (10000, отдельная
  константа от `StoneDepositReserve` — специально не общая, чтобы баланс
  можно было развести в будущем не трогая камень). Генерация —
  `seedOreDeposits`/`growOreRegion`/`findOreStart`/`oreScatterScore`,
  прямая копия `seedStoneDeposits` и компании с параметризованным `kind`
  (тасует форму по-разному для каждой руды, потому что хэш `oreScatterScore`
  включает `kind`), намеренно не объединена с камнем в одну функцию —
  ниже риск при последующей правке одного вида случайно сломать другой.
  Доли карты — уголь 4-8%, железная руда 2-4%, золотая руда 1-2%
  (`coalMinPercent`...`goldOreMaxPercent` в `cmd/game/main.go`) — угля
  специально больше, как и просил пользователь. **`minDepositDistanceFromWarehouse`
  (10 клеток, было 20 до уменьшения карты вдвое — см. "Процедурная
  карта")** — по прямому запросу пользователя ни один вид
  месторождения — камень, уголь, золотая руда, железная руда — не может
  заспауниться ближе этого расстояния от изначального склада (первая
  версия ограничивала только золото/железо и не трогала камень/уголь;
  пользователь затем явно попросил распространить его на все четыре
  вида). `seedOreDeposits`/`growOreRegion`/`findOreStart` **и** их
  каменные аналоги `seedStoneDeposits`/`growStoneRegion`/`findStoneStart`
  все принимают одинаковую пару `avoid gridPoint, minDistance int` (0 —
  без ограничения, оставлено ради тестов, которым нужно проверять только
  проценты обилия отдельно от дистанции) и делят одну функцию
  `tooCloseToPoint` (Евклидово расстояние) — проверяют её и на кандидате
  старта региона, и на каждой клетке при росте blob'а; если рост
  натыкается на исключённую зону, эта ветка роста просто не продолжается
  дальше (тот же приём, что уже применялся к непроходимым клеткам через
  `!CanPlace`), а не "перепрыгивает" через запретную зону. При загрузке
  старого сохранения (`loadGame`) точка отсчёта — координаты склада **из
  самого сохранения** (`findWarehouse` вызывается один раз, до
  `ensureStoneDeposits`/`ensureOreDeposits`, а не после), а не
  фиксированные `warehouseX,warehouseY` — старый город мог стоять не на
  дефолтном месте.
- **`save.GameState.OreSeeded`** — тот же паттерн, что `StoneSeeded`, один
  флаг сразу на все три вида руды (они всегда генерируются вместе за один
  вызов `NewGame`), не три отдельных флага.
- **Циклическая очередь добычи, а не "иди к ближайшему".** Раньше это не
  было нужно (Каменоломня — единственный вид ресурса), но с тремя видами
  руды рудокоп, идущий всегда к ближайшему месторождению, зациклился бы на
  одном виде. `miner.DefaultQuota = [{GoldOreDeposit,GoldOre,1},
  {IronOreDeposit,IronOre,1},{CoalDeposit,Coal,3}]` — **у каждого рудокопа
  своя** пара счётчиков `quotaIndex`/`quotaProgress` (не общая на
  контроллер), так что несколько рудокопов не толкутся синхронно на одном
  и том же шаге очереди. `startDepositJob` пробует текущий пункт очереди,
  и только если до него сейчас не добраться (например, месторождение этого
  вида ещё не открыто или выработано) — перебирает остальные пункты по
  кругу, сдвигая указатель очереди лишь тогда, когда реально пришлось
  пропустить шаг, а не при каждом проходе.
- **Плавильня — одно здание с двумя рецептами, а не два отдельных
  здания.** Прямой ответ на "может плавильню одну и исходя из того что
  сейчас плавится то и получается на выходе". Новое поле
  `building.Type.AltRecipes []Recipe` (пусто у всех 13 прежних видов
  зданий — строго аддитивное расширение, не меняет их поведения) и
  `Type.AllRecipes()`, возвращающий основной `Recipe` + `AltRecipes`,
  отфильтрованные по `TicksToProduce > 0`. `Building.ActiveRecipe int`
  запоминает, какой рецепт сейчас (или последним) выполнялся —
  используется для честного (round-robin, а не "первый рецепт всегда
  выигрывает по индексу") выбора: `economy.pickRecipe` начинает перебор
  со следующего после `ActiveRecipe` индекса и оборачивается по кругу.
  `economy.tickMultiRecipe` — отдельная ветка `TickWithConnectivity` для
  зданий с более чем одним рецептом, не трогает путь для обычных зданий
  (`tickRecipe`/`tickPrepaidRecipe`). **Явное ограничение, задокументированное
  в коде:** `Recipe.ConsumeInputsAtStart` не поддерживается вместе с
  `AltRecipes` — комбинация ни разу не понадобилась, но никто не проверял
  её совместно, так что лучше явно запретить в комментарии, чем словить
  тихий баг, если кто-то добавит такое здание позже.
- **`miner.Event.CargoResource`** — то, чего не было у `quarry.Event`:
  каменотёс всегда носит один и тот же `StoneBlock`, поэтому при смерти
  рабочего с грузом на руках достаточно знать количество. Рудокоп может
  нести любую из трёх руд/угля, поэтому `WorkerDied` обязан нести тип
  груза, а не только количество — иначе `cmd/game` вернуло бы потерянный
  груз на склад не тем ресурсом.
- Рендер месторождений руды (`render.drawOreDeposit`) — тот же приём, что
  `drawStoneDeposit` (тон плавно бледнеет к выработке), но своя пара
  цветов на вид руды. У трёх месторождений, хижины рудокопа, Плавильни,
  и юнитов Miner/Smelter теперь есть собственный отдельный арт (заменил
  первоначальные переиспользованные спрайты-заглушки — см.
  `internal/assets/assets.go` и `internal/assets/generated/`).

## Процедурная карта

По прямому запросу пользователя ("что у нас дальше?" → карта и генерация;
"карта генерируется случайно при 'Новой игре', и подумай над размером
моря") карта больше не одна и та же зашитая раскладка
(`world.NewTestGrid`, оставлена только для тестов, которым просто нужна
хоть какая-то сетка) — `NewGame` строит её заново каждый раз через
`generateGrid(mapWidth, mapHeight, seed)` в `cmd/game/main.go`. Мировая
логика (world.Grid/Tile) осталась в `internal/world`, вся процедурная
генерация — в `cmd/game`, тем же паттерном, что уже был у
seedTrees/seedStoneDeposits/seedOreDeposits:

- **`mapWidth, mapHeight = 50, 38`** — заменяет прежние зашитые 40×30
  (`world.NewTestGrid`). Только размер фиксирован, раскладка внутри него —
  нет. Было 100×75 (само по себе уже увеличение исходных 40×30) — по
  прямой просьбе пользователя ("уменьши карту в 2 раза") карту уменьшили
  обратно вдвое. Обилие ресурсов при генерации (проценты моря/руды/чащ,
  плотность деревьев/рыбы) выражено в процентах площади карты, так что
  масштабируется само, без отдельной правки. А вот все константы, что
  измеряют расстояние в клетках, а не в процентах карты, пришлось
  уменьшить вручную вместе с картой — иначе, например, "не дальше 20
  клеток от воды" на карте вдвое меньшей ширины стало бы значить "почти
  через всю карту", а не "рядом": `minDepositDistanceFromWarehouse`
  (20→10), `maxWarehouseDistanceFromWater` (20→10), `warehouseEdgeMargin`
  (6→3), `treeRegrowthRadius`/`fishRegrowthRadius` (20→10 у обоих).
  `treeRegrowthLocalCap` (12→3) уменьшен не вдвое, а вчетверо — это
  плотность на **площади** локального радиуса (`treeRegrowthRadius`), а
  площадь круга падает с квадратом радиуса: `12 * (10/20)² = 3` сохраняет
  ту же плотность ~1%, на которую исходную пару чисел и подбирали (у
  рыбы такой отдельной константы нет — `fishBodyLimit` считает те же 40%
  прямо от фактического числа клеток в обрезанной по радиусу секции, так
  что пересчитывать вручную не нужно). `MaxWorkRadius` профессий
  (лесоруб/каменотёс/рудокоп, см. "Голод: два реальных бага..." выше) **не
  трогали** — тот бюджет откалиброван от запаса сытости, а не от размера
  карты, и меньшая карта делает достижимость только легче, никогда не
  хуже.
- **`newMapSeed()`** — единственное место в файле, где зерно **не**
  фиксированная константа: `uint32(time.Now().UnixNano())`. У всех
  остальных `*Seed` (деревья/рыба/камень/руда) есть причина быть
  фиксированными (регенерация после загрузки старого сохранения должна
  быть воспроизводима/один раз) — у самой карты такой причины нет, она
  никогда не пересоздаётся повторно: весь тайловый грид уже целиком
  сохраняется как есть (`save.GameState.Tiles`), так что зерну не нужно
  переживать загрузку вообще.
- **Море — единая полоса вдоль ЦЕЛОГО края карты, а не blob, который
  просто где-то касается края.** Первая версия (`growSeaRegion` через
  BFS-blob от одной точки на краю, тот же приём, что у
  `growStoneRegion`) не устроила пользователя: "вода должна быть скраю
  карты единая на границе с краем карты" — blob мог коснуться края всего
  одной клеткой, а не тянуться вдоль всей его длины. Текущая версия
  вообще не растёт из одной точки: для каждой позиции вдоль случайно
  выбранного края (`growSeaRegion`, координата — либо X для верх/низ,
  либо Y для лево/право) считается своя глубина ухода вглубь карты, и эти
  глубины образуют **сглаженное, тяготеющее к среднему случайное
  блуждание** (xorshift32-шаг ±1 на позицию, с "подтягиванием" к
  `avgDepth`, если ушли выше или ниже) — оттого вся длина края гарантированно
  вода (просто "единая полоса"), а внутренняя граница неровная и
  органичная, а не идеальная прямая линия и не рваный шум. Размер —
  8-14% площади карты (`seaMinPercent`/`seaMaxPercent`) — прямой ответ на
  "подумай над размером моря": достаточно большое, чтобы читаться
  настоящим побережьем и вместить несколько хижин рыбака вдоль него, но
  не больше примерно седьмой части карты, чтобы основная часть осталась
  сухой застраиваемой землёй. **Пахотные поля/`world.Fertile` вообще не
  генерируются** — по прямому запросу пользователя ("пахотные поля не
  генерируем вообще! коричневые области"); `world.Fertile` как тип
  рельефа остался в `internal/world` только потому, что старые
  сохранения, сделанные до этого решения, всё ещё могут его содержать
  (`Farm` и так строится на любой сухой клетке независимо от рельефа, см.
  `building.Type.CanBuildOn` — визуальной подсказки без косметики не
  жалко).
- **`findWarehouseSpot` выбирает случайное место, а не ближайшее к
  центру.** Первая версия центрировала склад — пользователь явно попросил
  "перегенерируем расположение респауна и карты в случайном порядке":
  теперь среди всех клеток обычной травы (`world.Grass`, не `Water`) со
  свободным местом под стартовую дорогу южнее (`Buildable()`), не ближе
  `warehouseEdgeMargin` (6 клеток) к любому краю карты, выбирается
  случайная — тем же приёмом "самый низкий хэш побеждает", что и везде в
  этом файле, зерно передаётся отдельно от зерна самой карты
  (`mapSeed^0xc2b2ae35`). При неудаче (не должно случаться при текущих
  процентах моря, но игра не должна падать, если всё-таки случится) —
  тот же поиск без отступа от края, а если и это не сработает — голый
  центр карты без проверки рельефа.
- **Чащи (`seedThickets`/`growThicketZone`) — добавляют деревья, а не
  заменяют равномерный разброс.** Вызывается в `NewGame` сразу после
  `seedTrees`, отдельным зерном. Внутри зоны (тот же blob-рост, что у
  месторождений, но проверка размещения — `building.CanPlace(...,
  building.Tree, ...)`) дерево ставится не на каждой клетке, а с
  вероятностью `thicketDensityPercent` (45%) — иначе чаща выглядела бы
  сплошной стеной стволов, а не густой рощей. Побочный эффект: на
  свежей карте общее число деревьев (равномерный разброс + чащи) уже
  превышает потолок `seedTrees`'а собственного 1%-от-карты — это значит,
  что `tickTreeRegrowth` не станет досаживать новые деревья взамен
  срубленных, пока игрок не сведёт общее число ниже этого потолка. Не
  баг, ожидаемое побочное поведение существующего потолка регенерации.
- **`Game.resetToNewGame()` (см. "Вкладка Опции" ниже) тоже проходит
  через `NewGame()` целиком** — кнопка "Новая игра" получает новую
  процедурную карту так же, как первый запуск игры, а не переиспользует
  старую.

**Два реальных бага с производительностью, которые вскрыла именно бо́льшая
карта.** Пользователь сообщил "большая нагрузка на ЦП и игра просто
зависает" — оба бага существовали в коде и раньше, но были почти
незаметны на старой карте 40×30 с десятками месторождений; на новой
100×75 с сотнями отдельных `Building`-объектов месторождений (каждая
клетка руды/камня — свой объект, не единый регион) они превратились в
настоящий стопор:

- **`pathfind.landWalkable` пересканировал весь `buildings` на КАЖДУЮ
  клетку BFS.** `FindLandPath` (единственный способ передвижения
  лесоруба/каменотёса/рудокопа/строителя/слуги-с-стройматериалами —
  свободного хождения не по дорогам) был `O(посещённых_клеток ×
  количество_зданий)` из-за `landWalkable`, линейно сканировавшего
  `buildings` при проверке КАЖДОЙ соседней клетки в BFS. Почти незаметно
  при сотне зданий на маленькой карте — но с ростом карты выросли и
  количество клеток BFS (~6x), и количество зданий (месторождения растут
  вместе с площадью карты, счёт может идти на тысячи) — итоговое
  замедление перемножается, а не складывается. **Исправлено**:
  `pathfind.buildingOccupancy` строит индекс занятых клеток ОДИН раз в
  начале `FindLandPath`, а не при каждой проверке соседа — `landWalkable`
  теперь просто O(1)-подстановка в карту. Регресс-тест
  `TestFindLandPathStaysFastWithManyBuildings` держит бюджет по времени
  (200ms) с тысячами зданий на карте 100×75 — если кто-то опять протащит
  builder-scan обратно внутрь BFS, тест это поймает.
- **Список исключений для маркера доступа не обновили при добавлении
  руды/угля.** `Draw()` рисует зелёную/красную точку доступа
  (`ui.DrawAccessMarker`) почти на каждом здании **каждый кадр** (60
  раз/сек, не раз за тик симуляции!), а для этого вызывает
  `g.buildingConnected(b)` — полный `pathfind.FindPath` (BFS) на каждое
  здание. Когда добавлялась Каменоломня, `StoneDeposit` явно исключили из
  этого цикла (месторождению не нужна отметка доступа). Когда позже
  добавились уголь/руда, три новых вида месторождений в исключения
  добавить забыли — то есть КАЖДОЕ месторождение угля/золота/железа на
  карте гоняло полный BFS 60 раз в секунду. На маленькой карте с
  десятками месторождений это было незаметно; на большой с сотнями —
  напрямую вызывало симптом "большая нагрузка на ЦП, игра зависает".
  **Исправлено**: исключение вынесено в отдельную функцию
  `showsAccessMarker(kind)` (легче тестировать и не забыть в следующий
  раз при добавлении нового вида месторождения), включает все четыре
  конечных вида — `StoneDeposit`/`CoalDeposit`/`GoldOreDeposit`/`IronOreDeposit`.
  Тест `TestShowsAccessMarkerExcludesEveryDepositKind` держит список в
  синхроне.
- Оба бага в сумме и объясняют жалобу пользователя: `landWalkable` бил по
  каждому вызову перемещения юнита (нечасто, но дорого), а
  `showsAccessMarker` — по каждому кадру отрисовки (часто и тоже дорого)
  — вместе они делали и симуляцию, и просто рендер ощутимо тяжелее с
  ростом карты.

## Золото и наём

По прямому запросу пользователя достройка здания и появление в нём
работника — теперь два независимых, оба платных действия:

- **`resource.Gold`** — чистая валюта, не груз: ни одно здание её не
  производит и не принимает, ни один слуга её не носит (специально не
  добавлена ни в один `Recipe.Inputs`/`Output`, поэтому `findDirectJob`/
  `findSupplyJob`/`findCollectJob` её никогда не тронут). Она просто лежит
  в общем `Stockpile` и списывается напрямую, в момент найма.
- **`cmd/game.trySpendGold`/`canAffordHire`** — единая точка списания
  (`unitHireCost = 1`) для абсолютно всех наймов: слуги (`hireSerf`),
  любой профессии (`hireVillagerInto`), лесоруба/рыбака/каменотёса/рудокопа/
  строителя (ветки `hireFromTab`). `canAffordHire` дополнительно
  используется в `hireOptions`, чтобы карточка выглядела недоступной
  ещё до клика, а не только после неудачной попытки.
- **`finishConstruction` больше не вызывает `spawnWorkersFor`.** Готовое
  здание — как здание, у которого только что умер работник: пустое, с
  красной подсветкой (`unstaffedWorkerBuildings`), ждёт найма через
  вкладку "Найм". `spawnWorkersFor` не удалена — её последний вызывающий
  это миграция старых сохранений (`len(state.Units) == 0` в `loadGame`),
  которая по-прежнему подразумевает старое, дореформенное поведение.
- **Реальный баг, пойманный до релиза:** после того как автоспавна не
  стало, найм в первое совпавшее здание (`hireVillagerInto`, ветки
  `HireLumberjack`/`HireFisherman`/`HireQuarryman`) обязан проверять
  `b.ConstructionStage == building.ConstructionNone`, иначе игрок мог бы
  нанять фермера в ферму, которая ещё физически не достроена (строитель
  копает фундамент, а житель уже "внутри"). `hireOptions`'s
  `countBuildings` по той же причине считает только достроенные здания —
  иначе `Limit`/`Available` врали бы про вакансию, которой на самом деле
  ещё нет.

## Наём и панель слева

Левая панель — три вкладки, переключаются кликом (`ui.LeftTab`,
`Layout.MenuTabAt`): "Стройка", "Найм" и "Опции" (настройки — см. ниже).
`Layout.tabRect(i)` — общая геометрия кнопки вкладки `i`, используется и
отрисовкой (`drawMenuTabs`), и хит-тестом (`MenuTabAt`), поэтому три кнопки
не могут разъехаться. На вкладке найма —
карточка на каждую профессию плюс слуга. Слуга — без лимита; любая
профессия доступна к найму только если есть **хотя бы одно свободное
здание нужного вида** (`Controller.HasHome` в каждом из пакетов
юнитов) — это одновременно и решает "нанять именно свиновода, если умер
именно он", и естественным образом не даёт NPC стать больше числа зданий
(слуги в этот подсчёт не входят — по прямому запросу пользователя).
Строитель — второе исключение после слуги, но по другой причине: лимит не
"без ограничения", а фиксированные 3 (`maxBuilders`), потому что у него
нет здания, по которому лимит вообще можно было бы считать — см. "Стройка"
выше.
`Game.hireOptions()` строит список карточек, `Game.hireFromTab` находит
первое свободное здание нужного вида и сажает туда нового работника —
тот же путь, которым здание получает работника при постройке
(`spawnWorkersFor`).

Выбор объекта на карте (`Game.selectionAt`) — **правило дважды менялось,
дважды по прямому запросу пользователя, в итоге прямо противоположно
исходному**:

- **Изначально**: юнит перехватывает клик у здания, только если он
  реально отрисован на этой клетке (`VisibleOnMap()`) — иначе пекарь,
  стоящий "внутри" пекарни невидимо, крал бы клик у самого здания.
  Слуга и строитель — особый случай без этой проверки вовсе, у обоих
  физически нет здания, внутри которого можно спрятаться, так что юнит
  побеждает **всегда**.
- **Затем design сменился на противоположный** (не мной — застал уже
  готовым в коде и тестах с переименованными ожиданиями:
  `TestSelectionAt_BuildingWinsOverVisibleFarmer`,
  `TestSelectionAt_ConstructionSiteWinsOverBuilder`,
  `TestSelectionAt_WarehouseWinsOverSerf`): **здание побеждает всегда**,
  даже видимого фермера на поле, даже строителя на стройплощадке, даже
  слугу на складе — клик по инспектируемому объекту (ферме, стройке,
  складу) должен всегда доходить до него, а не до случайно проходящего
  мимо юнита.
- **Реальный баг, найденный пользователем в игре**: это правило без
  исключений задело дороги — `Road` тоже здание, а слуги (и вообще все
  юниты) проводят на дорогах почти всё время в пути. В итоге выбрать
  идущего по дороге юнита стало physически невозможно: клик всегда
  попадал в дорогу. **Исправлено** точечным исключением: `selectionAt`
  запоминает клетку дороги (`roadHit`), но не возвращает её сразу —
  сначала проверяются все юниты, и только если на клетке никого нет,
  функция откатывается к дороге. Для любого другого здания (ферма,
  склад, стройплощадка) правило "здание побеждает" осталось прежним, не
  тронуто. Закреплено `TestSelectionAt_SerfOnRoadWinsOverTheRoad` (обе
  половины: юнит на дороге побеждает; дорога без юнита на клетке всё ещё
  выбирается как раньше) плюс всеми четырьмя тестами `*WinsOver*` выше,
  подтверждающими, что для не-дорожных зданий ничего не сломалось.

Вместо отрисовки юнита поверх здания или индикатора +/- — строка "Людей
внутри: N" в инспекторе выбранного здания (`Game.unitsAt`, считает вообще
всех, кто физически стоит на клетках здания, не только "приписанного"
работника — поэтому работает и для склада/харчевни, у которых нет
`RequiresWorker`).

## Вкладка "Опции": язык, скорость, новая игра, 5 именованных слотов сохранения

Третья вкладка левой панели (`ui.SettingsTab`) объединяет то, что раньше
было разбросано по клавишам и нижней панели. По прямому запросу
пользователя ("убери быстрые клавиши "L", "S", 1-Q и т.д.") **вся
навигация построек, сохранение и загрузка теперь только мышью** — нет
`paletteKeys`/`handlePaletteSelect` (числовые клавиши 1-0/Q больше не
выбирают тип постройки, только клик по карточке), нет `handleSaveLoad`
(клавиши S/L и файл-квиксейв `saves/slot1.json` удалены целиком) — H
(нанять слугу), Delete (удалить выбранное) и Esc (выход/отмена диалога)
остались, пользователь их не называл:

- **язык** — две кнопки (RU/EN), клик сразу зовёт `i18n.SetLang`; никакого
  кеширования строк нигде нет — каждый `DrawText` в игре читает
  `i18n.T()` заново каждый кадр, поэтому смена языка видна в тот же кадр,
  без перезапуска;
- **скорость** — та же пятёрка кнопок, что и в нижней панели (`SpeedAt`),
  но своя копия в левой панели (`SettingsSpeedAt`) — они не связаны кодом,
  просто рисуют одно и то же состояние `g.sim.Speed()` из двух мест;
- **"Новая игра"** — полноширинная кнопка между строкой скорости и списком
  слотов (`SettingsNewGameAt`, всегда видна, как язык/скорость — не
  исчезает, пока открыт диалог сохранения). Клик открывает
  `ui.DialogConfirmNewGame` (третий `DialogKind`, тот же общий механизм
  диалогов, что у подтверждения перезаписи слота, и та же геометрия кнопок
  `SettingsDialogButtonAt`), а не сбрасывает город сразу — необратимое
  действие без подтверждения было бы неприятным сюрпризом от случайного
  клика. Подтверждение вызывает `Game.resetToNewGame()`: строит целиком
  свежий `*Game` через обычный `NewGame()` и заменяет им текущий
  (`*g = *fresh`), сохраняя только активный `g.layout` (и пересчитывая по
  нему вьюпорт свежей камеры) — иначе сброс на секунду откатил бы размер
  панелей к дефолтным 1024x768 в уже развёрнутом окне. Активный язык
  (`i18n` — не поле `Game`, пакетная переменная) переживает сброс сам
  собой.
- **5 именованных слотов сохранения**. Каждый слот — свой файл
  `saves/panel_slot_N.json` (`slotPath(n)`, N=1..5), с полным
  `save.GameState` плюс поле `Name` (до 10 рун, не байт — кириллица
  считается буквами, а не UTF-8 байтами).

Слот показывает имя или прочерк ("— пусто —"), с кнопками "Сохранить"/
"Загрузить"; кнопка загрузки визуально приглушена и неактивна для пустого
слота. Клик по "Сохранить":
- пустой слот → сразу открывает диалог ввода имени (`ui.DialogNaming`);
- занятый слот → сперва диалог подтверждения перезаписи
  (`ui.DialogConfirmOverwrite`, показывает текущее имя), и только после
  подтверждения — тот же диалог ввода имени, предзаполненный старым именем.

Оба диалога рисуются на месте списка слотов (`drawSettingsDialog`) и делят
одну и ту же геометрию кнопок (`SettingsDialogButtonAt`: левая половина —
подтвердить, правая — отмена), чтобы контролов для хит-теста было ровно
два набора, а не четыре. Пустое имя при подтверждении не сохраняется как
есть — подставляется `"Слот N"` (`SlotDefaultName`), чтобы слот не остался
безымянным.

**Пока открыт диалог, `Game.Update()` не вызывает обычные обработчики ввода
вообще** (`g.handleMouse/handleUnitActions` пропускаются целиком, см.
развилку в начале `Update`) — иначе клик мимо диалога попутно выбрал бы
постройку в палитре или удалил бы выбранное здание, а Escape для отмены
диалога закрыл бы всю игру (тот же `KeyEscape`, которым обычно выходят).
Ввод текста (только для `DialogNaming` — `DialogConfirmOverwrite` и
`DialogConfirmNewGame` не набирают текст) — с нуля, готового
виджета в Ebiten нет: `ebiten.AppendInputChars(nil)` за кадр отдаёт
только что введённые руны, `inpututil.IsKeyJustPressed(ebiten.KeyBackspace)`
стирает последнюю. Символы `< ' '` (управляющие, включая сам Enter) явно
пропускаются, иначе Enter дописывался бы в имя перед тем, как закрыть
диалог.

`Game.slotCache []ui.SaveSlotInfo` держит имена и занятость всех пяти
слотов, обновляется явно (`refreshSlotCache`) при старте игры и сразу
после успешного сохранения в слот — **не** каждый кадр: `save.PeekName`
хоть и не гоняет через миграцию версий, всё равно читает и парсит весь
JSON-файл целиком, а `Draw()` вызывается 60 раз в секунду, так что вкладку
настроек кэш избавляет от дискового IO на каждый кадр отрисовки.

### Автосохранение

По прямой просьбе пользователя ("включается в Опции напротив слота,
сохраняет прогресс каждые 2000 тиков (или по времени), подумай сам") —
переключатель "Авто" у каждого из 5 слотов, а не отдельная шестая
"автосохранение"-настройка. Design-решения, принятые самостоятельно (была
явная просьба "подумай сам"):

- **Тики симуляции, не время.** Пользователь предложил выбор между
  "каждые 2000 тиков" и "по времени" — взял тики: это тот же масштаб,
  которым уже меряется всё остальное в игре (голод, рост, производство),
  и это согласуется с тем, что скорость симуляции у игрока настраиваемая
  (0.5x-8x) и её можно поставить на паузу — автосохранение, завязанное на
  тики, естественно молчит на паузе и ускоряется/замедляется вместе со
  скоростью игры, а не тикает независимо от того, идёт игра или нет.
  `autosaveIntervalTicks = 2000` — это ≈1000 симуляционных секунд
  (framesPerSimTick=30, 60 fps ⇒ 2 тика/сек на Normal), то есть примерно
  16-17 минут игрового времени на обычной скорости.
- **Одна цель за раз, не список.** `Game.autosaveSlot int` (0 = выключено)
  — ровно один слот может быть целью одновременно; включение нового слота
  само выключает старый, отдельно выключать не нужно
  (`toggleAutosaveSlot`). Разложить на 5 независимых включаемых слотов
  означало бы до 5 сохранений подряд каждые 2000 тиков — бессмысленная
  трата, раз это один и тот же прогресс одной и той же партии.
- **Не персистентно между запусками, как язык и скорость.** В проекте и
  так уже нет отдельного файла настроек — язык/скорость живут только в
  памяти текущей сессии, сбрасываются при перезапуске. `autosaveSlot`
  специально сделан таким же: не пишется ни в один `save.GameState`, при
  свежем запуске игры всегда выключено. Не трогается ни `resetToNewGame`,
  ни `loadGame` — это настройка панели, а не часть партии.
- **Тихо, без диалогов.** Обычное сохранение через кнопку идёт через
  `ui.DialogNaming`/`ui.DialogConfirmOverwrite` — автосохранение не может
  себе этого позволить, весь смысл в том, чтобы не прерывать игру.
  `Game.autosave()` — прямой вызов `saveGame(slotPath(...), name)`,
  минуя диалоги целиком; имя берётся из уже сохранённого в слоте
  (`slotCache`), а для самого первого автосохранения в пустой слот —
  тот же дефолт ("Слот N"), что и у обычного сохранения с пустым
  введённым именем.
- **`tickAutosave()` вызывается там же, где и весь остальной тик
  симуляции** (`Game.Update`, внутри `for range g.sim.Advance()`), не в
  `Draw` — иначе интервал зависел бы от FPS отрисовки, а не от тиков.
- **Проверено реальной записью на диск, не только состоянием в памяти** —
  `TestTickAutosave_FiresAfterIntervalAndWritesTheSlot`
  (`cmd/game/main_test.go`) реально досчитывает до
  `autosaveIntervalTicks` и проверяет файл через `os.Stat`/
  `save.PeekName`, с очисткой за собой (`t.Cleanup`). Безопасно для
  повторных прогонов `go test`: рабочая директория тестового бинаря —
  каталог пакета (`cmd/game`), а не корень репозитория, так что
  `slotPath` во время теста пишет в `cmd/game/saves/...`, а не
  затирает настоящее `saves/panel_slot_N.json` пользователя в корне.

**Не используй `ebitenutil.DebugPrint`/`DebugPrintAt` нигде в этом проекте.**
Его встроенный шрифт покрывает только U+0000–U+00FF (см. его собственный
doc-комментарий) — кириллица с ним просто не рисуется, молча. Весь текст
идёт через `ui.DrawText` (`internal/ui/text.go`), который использует
`text/v2` + `github.com/hajimehoshi/bitmapfont/v4` (уже зависимость Ebiten,
его битмап-шрифт покрывает кириллицу — проверено вручную через
`GlyphBounds`). Один шрифт на всю игру, один пакет, где его менять.

**Важно про `ebiten.DrawImageOptions`/`text.DrawOptions`:** их zero-value
`CompositeMode` — это `CompositeModeCustom` (не `SourceOver`!) с zero-value
`Blend`. На практике почти всегда нужно **явно** ставить
`op.Blend = ebiten.BlendSourceOver` — без этого поведение композитинга не
гарантировано быть обычным alpha-blending. См. `render/sprite.go` и
`ui/text.go`, где это уже сделано с комментарием.

## Локализация

Все строки, которые видит игрок (HUD, подсказки, статусы, заголовок окна),
идут через пакет `i18n`, не хардкодом в `ui`/`cmd`:

- `i18n.Catalog` — набор полей на один язык; `i18n.T()` возвращает каталог
  активного языка, `i18n.SetLang(lang)` его переключает.
- Один язык — один файл (`ru.go`, `en.go`, ...), регистрирующий себя через
  `init()` → `register(lang, Catalog{...})`. Добавить новый язык — значит
  добавить один новый файл, не трогая остальной код.
- Активный язык сейчас жёстко задаётся в `main()` (`i18n.SetLang(i18n.RU)`
  — русский по умолчанию); выбора языка в самом UI игры пока нет, это
  следующий шаг, если понадобится.
- Внутренние идентификаторы (`resource.Type.String()`, ключи в JSON
  сохранений, `building.Type.Name`) намеренно остаются на английском для
  стабильности формата — локализуется только то, что реально выводится на
  экран.

## Сборка и запуск

```
go run ./cmd/game          # запуск с исходников
go build ./cmd/game        # десктоп-бинарник под текущую ОС
go test ./...              # юнит- и интеграционные тесты
```

Кросс-компиляция под другую ОС — через переменные `GOOS`/`GOARCH`. Сборка
под браузер — `GOOS=js GOARCH=wasm go build -o game.wasm ./cmd/game` плюс
`wasm_exec.js` от Ebiten и простая HTML-обёртка. Порт на Android —
отдельный будущий шаг через `ebitenmobile`, пока не начат.

**`tools/build.ps1`** — по прямому запросу пользователя: готовая раздача
для Windows одной командой (`bin\strategy_game.exe` +
пустая `bin\saves\` рядом). Уточнил у пользователя, что имелось в виду
под "ассеты отдельной папкой" — ответ: ассеты уже вшиты в бинарник через
`go:embed` (`internal/assets`), отдельная папка с PNG во время работы
не нужна вообще, так и оставили — скрипт просто собирает exe и создаёт
пустую `saves\` рядом, `bin\` целиком самодостаточен и годится под zip.
`-Release` добавляет `-ldflags "-s -w"` (без отладочных символов, exe
заметно меньше) — **не** используется по умолчанию: проект ещё активно
разрабатывается, а без символов трассировка паники в баг-репорте куда
менее полезна. `-Clean` стирает `bin\` перед сборкой. Отдельно проверяет
занятость `bin\strategy_game.exe` (`[System.IO.File]::Open` на
запись) до вызова `go build` — иначе стандартная ошибка Go в этом
случае ("Access is denied") легко принимается за что-то другое, а не
за "закрой запущенную игру сначала".

## Графика

Активный набор `internal/assets/generated` — компактные оригинальные
64×64 пиксельные PNG для рельефа, зданий и юнитов; прежние заглушки из Kenney
лежат рядом как legacy-ассеты (см. `internal/assets/CREDITS.md`). Карта —
квадратная top-down сетка, а здания используют объёмные ("стоящие") спрайты
выше своей клетки. Это НЕ настоящая изометрия — координатная математика
(`render.Camera`, `TileToScreen`) осталась прежней, квадратной; поменялась
только отрисовка.

- `internal/assets` эмбедит PNG через `go:embed` и декодирует их в
  `*ebiten.Image` один раз при старте (`mustLoad`/`mustComposite`).
- `render.drawStanding` (`render/sprite.go`) — общая функция отрисовки:
  масштабирует спрайт под `tilesTall` тайлов высотой, прижимает к низу и
  центрирует по горизонтали на клетке. `tilesTall=1` — для тайлов земли,
  `buildingHeight=1.7` (`render/buildings.go`) — для зданий, чтобы они
  визуально "вставали" выше своей клетки.
- Footprint Mill/Bakery/Warehouse/Tavern/LumberjackHut/FisherHut/PigFarm/
  MeatWorkshop — **1×1**: в этом паке здание — это один тайл с высоким
  спрайтом, а не несколько клеток. **Farm и Winery — 3×3**: один угол
  занимает здание (`assets.FarmHouse`/`assets.Winery`, стоящий спрайт как
  у остальных зданий), остальные 8 клеток — поле/виноградник
  (`assets.Fertile`, тонированное по прогрессу цикла, см. `lerpColor` в
  `render/buildings.go`) — так и "иконка", и "поле вокруг неё".
- `assets.MillFrames` сохраняет интерфейс трёх кадров и использует старое
  подробное тело мельницы с отдельными кадрами вращения лопастей.
- Юниты (`render/serfs.go`, `render/villagers.go`, `render/lumberjacks.go`,
  `render/fishermen.go`) используют отдельный силуэт и цвет для каждой
  профессии. При переносе над слугой появляется цветной маркер груза, а
  голодный юнит подсвечивается красным тоном. Во время движения добавлен
  лёгкий четырёхфазный bob. Юнит, "стоящий на посту" внутри своего
  здания, не рисуется вовсе (см. "Наём и панель слева" — `VisibleOnMap()`),
  кроме фермера/винодела, которых видно за работой на поле/винограднике.
- `render/draw.go` добавляет редкие двухфазные колышущиеся травинки на
  травяных тайлах, а `render/effects.go` — трёхфазный огонь над печью
  пекарни и стадии роста колосьев на полях. `render/lumberjacks.go` добавляет
  шаговый bob, груз бревна и жест рубки. Это процедурные эффекты, а не
  тяжёлые дополнительные спрайт-листы.
- `ui.DrawBufferLevels` подписывает каждое производственное здание
  компактным "вход→выход" (например "3→5") над ним — мониторинг остатков,
  который запросил пользователь, без захода в отдельное меню.
- **Если что-то рендерится подозрительно (пропадает, "срезается")** —
  сначала проверь свой ЖЕ инструмент диагностики, а не сам рендер. Заняло
  очень много времени вживую: `ebiten.Image.At()` через голый `image.Image`
  интерфейс — штатный и надёжный способ чтения пикселей, отдельно
  проверенный много раз; но если пишешь скрипт-скриншотер снаружи игры для
  сверки — перепроверь его логику (кроп/масштаб/порядок координат) в первую
  очередь, прежде чем подозревать Ebiten или свой код отрисовки.

### Автопереходы: дорожные соединения и границы рельефа

Первый пункт из ROADMAP.md "В работе" ("автопереходы текстур рельефа и
дорожных соединений"). Ни один из готовых тайлов не имеет отдельных
"соединительных" вариантов (нет прямой/угловой/T/крестовой графики дороги,
нет отдельного берегового тайла) — обе задачи решены не новым артом, а
процедурной коррекцией существующих 64×64 текстур поверх обычной
отрисовки, тем же приёмом, что уже использовался для голода/логистики в
этом проекте: посчитать реальную проблему по пикселям, а не на глаз.

- **Дорожные соединения** (`internal/assets/roadfade.go`,
  `render.drawRoadConnections`/`drawRoadFade` в `render/buildings.go`).
  Проблема была не в "нет соединительной графики" абстрактно, а
  конкретно измерена: `terrain_road_stone.png` имеет собственное тёмное
  виньетирование по краю (яркость ~61 у самого края, выходит на плато
  ~105 к глубине ~14-16px из 64) — из-за него любые два соседних тайла
  дороги читались как отдельные обрамленные плиты, а не один путь.
  Исправление — 4 предвычисленных при старте PNG-градиента
  (`assets.RoadFadeN/E/S/W`, тёплый серый с альфой, убывающей по
  экспоненте `roadFadeMaxAlpha * exp(-depth/roadFadeTau)`, коэффициенты
  подогнаны под реально измеренный профиль виньетки, не на глаз), которые
  рендерер докладывает поверх обычного тайла дороги через аддитивный
  блендинг (`ebiten.BlendLighter`) на той стороне, где сосед — тоже
  завершённая дорога (`finishedRoadPositions`, недостроенная дорога не
  считается — то же правило, что уже использует `pathfind.roadSet`).
  Аддитив, а не непрозрачная заплатка — коррекция гасит виньетку, но не
  стирает саму текстуру брусчатки под ней.
- **Границы рельефа** (`render.blendTerrainEdges`/`drawEdgeStrip` в
  `render/draw.go`). В генерации карты реально используются только два
  типа рельефа — `Grass` и `Water` (`Fertile`/`Forest`/`Stone` определены
  в `internal/world`, но `generateGrid` их никогда не красит — см. кусок
  про "пахотные поля не генерируем" выше), так что единственная граница
  в игре — берег. Вместо готового берегового тайла — 4 слоя (`
  terrainEdgeBands`) убывающей по глубине обрезки СОСЕДСКОЙ текстуры
  (ближайшая к границе полоса соседа, обычным `SourceOver` на
  нарастающей прозрачности), уложенные один на другой у каждой границы,
  где сосед отличается по рельефу — превращает жёсткую построчную смену
  цвета в мягкий многопиксельный градиент без отдельного берегового
  арта. Не завязано именно на Grass/Water — сработает для любой пары
  рельефов, если их в будущем добавят.
- **Как проверялось.** У `internal/render` нет собственных графических
  тестов (весь пакет требует реального `ebiten.Image`/GPU-контекста,
  которого нет в `go test`) — визуальная корректность обеих правок
  проверена вручную: временная программа `cmd/roadpreview` (создана,
  проверена, удалена в этом же заходе — не часть репозитория) реально
  запускала `ebiten.RunGame`, рисовала сцену через тот же путь кода, что
  и настоящий рендерер (включая масштаб `tilePixels=24`, реальный
  дефолтный размер тайла на экране, не 64px исходника), сохраняла кадр в
  PNG и показывала результат для визуальной сверки на глаз — та же
  техника, которую этот файл уже советует ("если пишешь
  скрипт-скриншотер снаружи игры... перепроверь его логику" — здесь она
  сработала как задумано: сверка подтвердила правильный результат уже
  со второй попытки). `finishedRoadPositions` — единственная чисто
  логическая (без рисования) часть обеих правок — покрыта обычным
  `go test` (`internal/render/roads_test.go`).

### Состояния зданий: нет сырья и переполненный выход

Второй пункт из ROADMAP.md "В работе". У зданий уже были три состояния
(недостроено, нет работника, не подключено дорогой — см. выше); по
прямому выбору пользователя (через `AskUserQuestion`, вариант
"Рекомендую" был выбран вместе с двумя остальными) добавлены ещё два:
здание простаивает, потому что не хватает сырья на входе, и здание
простаивает, потому что выходной буфер полон и никто не забирает готовую
продукцию.

- **`render.buildingStallReason`** (`internal/render/stall.go`) — чистая
  функция без побочных эффектов, которая **зеркалит** условия остановки
  из `economy.tickRecipe`/`tickPrepaidRecipe`/`tickMultiRecipe`
  (`hasAllInputs`/`hasOutputRoom`), а не изобретает собственное
  приближённое понятие "простаивает". Специально не импортирует
  `internal/economy` — эти два хелпера там неэкспортированы и
  представляют собой однострочные проверки карты, дешевле
  продублировать логику в `render` (у него уже есть доступ к
  `building.Types`/`InputBuffer`/`OutputBuffer`/`OutputLimit()`), чем
  заводить новую межпакетную зависимость ради этого. Важная тонкость,
  без которой индикатор постоянно бы ложно срабатывал: счётчик прогресса
  у обычного рецепта растёт **независимо** от наличия сырья ("Mill
  тикает даже без пшеницы" — см. комментарий у `tickMultiRecipe`), так
  что здание не "простаивает", пока `ProgressTicks < TicksToProduce` —
  серve ещё может успеть подвезти сырьё до конца таймера. Для
  `ConsumeInputsAtStart` (свиноферма) сырьё проверяется только в момент
  `ProgressTicks == 0` — пустой `InputBuffer` посреди роста свиньи это
  нормальное "уже покормили" состояние, а не остановка (тот же нюанс,
  который уже объяснён в разделе "Стройка" про `tickPrepaidRecipe`). Для
  Плавильни (`AllRecipes()` > 1) "нет сырья" означает **ни один** из
  рецептов не может начаться — то же правило, что и у `pickRecipe`.
  Покрыто `internal/render/stall_test.go` по одному тесту на каждый из
  трёх путей рецепта плюс "здание на стройке"/"у здания вообще нет
  рецепта" (Warehouse) — обе всегда `stallNone`.
- **`disconnected` теперь тоже параметр `render.DrawBuildings`**, а не
  вычисляется внутри рендера отдельным полным проходом. Причина —
  реальная опасность повторить старый CPU-баг (см. "Два реальных бага с
  производительностью" выше): `g.buildingConnected(b)` — это полный
  BFS-поиск пути, и в `Game.Draw` УЖЕ был один такой проход на каждое
  видимое здание (для зелёной/красной точки доступа, `showsAccessMarker`
  + `ui.DrawAccessMarker`). Наивно дёрнуть `g.disconnectedBuildings()`
  (старый метод, используется для `economy.TickWithConnectivity`, но
  **без** отсечения по видимости, раз в тик симуляции — это ему можно) ещё
  раз внутри `Draw` значило бы: не просто удвоить этот BFS-проход, а
  сделать его БЕЗ отсечения по видимости (`disconnectedBuildings`
  сканирует вообще все производственные здания, а не только видимые) —
  практически воспроизвести тот самый баг заново. Вместо этого `Game.Draw`
  теперь считает связность **один раз** в общем цикле по видимым
  зданиям (`visibleConnectivity`), отдаёт из него карту `disconnected` в
  `render.DrawBuildings`, а цикл отрисовки точки доступа ниже переиспользует
  ту же карту вместо собственного вызова `g.buildingConnected(b)` — то
  есть после этой правки на видимое здание приходится **тот же самый**
  один BFS-проход, что был и раньше, а не два.
- **Один язык, а не три отдельных цвета.** Первая версия дала "нет
  сырья" тот же красный тон, что у "нет работника", а "переполнен выход"
  — отдельный янтарный. Пользователь тут же указал на реальную проблему:
  простаивающее (но укомплектованное) здание и по-настоящему пустое
  выглядели неотличимо — оба заливались одним и тем же красным на весь
  footprint. **Исправлено**: красная заливка на весь footprint осталась
  только за `unstaffed` (по-настоящему пусто, никого нет); все три
  прочие причины простоя (нет сырья, переполнен выход, не подключено
  дорогой) сведены в один визуальный язык — небольшое, малозаметное
  "Zzz"-облачко над крышей (`render.drawIdleBubble`), а не заливка. Одна
  причина показа для всех трёх сразу — какая именно, всё равно объясняет
  инспектор по клику; на уровне беглого взгляда на карту важно только
  различить "тут вообще никого" от "тут кто-то есть, но застрял".
- **Позиционирование облачка — реальный найденный баг.** Первая попытка
  разместить его над зданием использовала `sy - tilePixels*buildingHeight`
  и промахнулась на целую клетку вверх (проверено скриншот-превью —
  облачко висело в воздухе далеко над крышей мельницы). Причина:
  `drawStandingScaled` крепит `tilesTall`-спрайт к **низу** своей клетки
  (`sy+tilePixels-drawnH`), а не к верху — формула без `+tilePixels`
  вообще не учитывала, что спрайт растёт вверх от нижнего края клетки, а
  не от верхнего. Исправлено на `sy + tilePixels - tilePixels*buildingHeight`,
  сверено скриншотом ещё раз.
- **Форма облачка — тоже потребовала итерации по живому фидбеку
  пользователя.** Первая версия — маленький сплошной кружок с "Zzz"
  внутри — прочитал сам пользователь как "шарик", попросил вместо него
  именно облачко, покрупнее и малозаметнее. Вторая версия рисовала три
  полупрозрачных круга (`vector.FillCircle`) прямо поверх экрана — но
  наложение отдельных полупрозрачных кругов **накапливает прозрачность**
  в зонах пересечения (классическая ошибка компоновки: три круга по 130/255
  альфы дают в центре ~88% непрозрачности, а не 51%), так что центр
  облачка выходил плотным белым пятном, а не равномерно блёклым.
  **Исправлено**: `assets.IdleCloud` (`internal/assets/cloud.go`) — облачко
  растеризовано ОДИН РАЗ при старте как единая плоская фигура (union трёх
  окружностей через простой перебор пикселей, без альфа-наложения), и уже
  ЭТА готовая фигура целиком затемняется одним вызовом
  `op.ColorScale.ScaleAlpha(0.4)` — гарантированно равномерная
  прозрачность по всей форме, без более тёмных пятен на стыках.

### Мелкий декор

Третий пункт из ROADMAP.md "В работе" — по выбору пользователя (оба
"Рекомендую"-варианта): мелкий декор на траве и декор у воды. Чисто
атмосферное, без нового арта — процедурные векторные фигуры
(`internal/render/decor.go`), тем же способом, что уже рисует
покачивающиеся травинки (`drawGrassSway`) и рамки месторождений.

- **Детерминированный редкий разброс, без сохранённого состояния.**
  `tileHash(tx, ty, multiplierA, multiplierB)` — тот же приём, что у
  `drawGrassSway` (хэш от координат клетки), но с другими множителями,
  чтобы декор не совпадал именно с клетками травяного покачивания.
  Выбор вида декорации и его точная позиция внутри клетки тоже
  выводятся из хэша — значит ничего не нужно сохранять в файл
  сохранения: перезагрузка карты детерминированно восстанавливает ту же
  картину декора без единого нового поля в `save.GameState`.
- **На траве** (`drawGrassDecor`) — примерно 1 клетка из 32 получает один
  из четырёх вариантов (камень, пень, цветок, куст), выбранный тем же
  хэшем. **У воды** — на клетке травы, граничащей с водой, вместо
  обычного декора рисуется галька у берега (`drawPebbles`); на самой
  граничащей клетке воды — камыши (`drawReeds`), примерно у трети таких
  клеток. `findShoreEdge` ищет первого отличающегося по рельефу соседа в
  фиксированном порядке N/E/S/W — этого достаточно, чтобы декор читался
  как "у берега", не обязательно реагировать на все стороны вогнутой
  береговой линии сразу.
- **Реальный баг при подборе размера, найденный только скриншотом.**
  Первая версия размера декора использовала тот же множитель `unit :=
  tilePixels/assets.TileSize` (0.375 при дефолтном зуме), что и
  спрайты, масштабируемые из 64px исходников (`drawStanding` и
  компания) — но эти фигуры рисуются напрямую пакетом `vector`, а не
  масштабируются из PNG, так что верной единицей отсчёта был сам
  `tilePixels`, а не производная от `assets.TileSize`. Итог — на
  скриншоте-превью декор был практически невидим (радиус камня — около
  1 экранного пикселя). Камыши изначально были ещё и не видны по другой
  причине: тёмно-зелёный цвет (63,105,55) при `alpha=235` был подобран
  "на глаз" и почти сливался с текстурой воды — отладочная версия ярко-
  розовым цветом подтвердила, что позиция и сама отрисовка были верны с
  самого начала, проблема была исключительно в контрасте цвета.
  Исправлено: все размеры декора выражены как доля `tilePixels`
  напрямую, цвет камышей заменён на более светлый и насыщенный зелёный.
- **Как проверялось** — тем же способом, что и автопереходы выше:
  временная программа (`cmd/decorpreview`, не часть репозитория),
  реально зовущая `render.DrawGrid` на тестовом гриде трава/вода,
  сохраняющая кадр в PNG для сверки на глаз; `findShoreEdge`/`tileHash`
  как чисто логические функции покрыты `internal/render/decor_test.go`.

### Линия маршрута выбранного юнита

Последний пункт из ROADMAP.md "Следующий этап": сам выбранный объект уже
подсвечивался рамкой (`ui.DrawSelectionMarker`), но не было видно, куда
именно он идёт — только текст маршрута в инспекторе ("откуда → куда"),
без визуальной линии по карте.

- **`RemainingPath()` — один и тот же метод, добавленный во все семь
  типов юнитов** (`logistics.Serf`, `villagers.Villager`,
  `lumberjack.Lumberjack`, `fishing.Fisherman`, `quarry.Quarryman`,
  `builder.Builder`, `miner.Miner`): все семь уже хранили `path
  []pathfind.Point` и `pathIdx int` неэкспортированными, тем же путём,
  что и раньше (см. "Стройка" выше про `startSiteJob` и общий паттерн
  профессий) — `RemainingPath()` просто отдаёт `path[pathIdx:]`, то есть
  клетки **впереди**, а не весь путь с самого начала (игроку интересно
  "куда идёт", а не "откуда шёл").
- **`ui.selectedUnitTile`** — общий хелпер, вынесенный из
  `DrawSelectionMarker`, который одним `switch` по `Selection.Kind`
  отдаёт текущую клетку юнита **и** его `RemainingPath()` разом. Раньше
  `DrawSelectionMarker` делал этот switch сам (длинная цепочка
  `if/else if`), а подсветки для Каменотёса/Строителя/Рудокопа в ней не
  было вообще — они просто отсутствовали как варианты (см. ROADMAP.md,
  реальный пробел, а не баг). Новая `ui.DrawSelectedRoute` использует тот
  же хелпер — значит подсветка рамки и линия маршрута гарантированно
  согласованы про "что вообще выбрано" одним и тем же кодом, а не двумя
  параллельными переключателями, которые могли бы разойтись при будущей
  правке.
- **Линия — соединённые отрезки через центры клеток** от текущей позиции
  юнита через каждую точку `RemainingPath()`, тем же полупрозрачным
  жёлтым, что и рамка выделения, но заметно бледнее (`alpha=150` против
  `255` у рамки) — рамка обозначает "вот этот объект", линия — "вот куда
  он идёт", это два разных по важности сигнала, не должны спорить за
  внимание.
- **Реальная тонкость, пойманная тестом, не осмотром.** Первая версия
  регресс-теста (`TestSerf_RemainingPath`,
  `internal/logistics/logistics_test.go`) предполагала, что
  `RemainingPath()` только монотонно укорачивается за всю поездку — тест
  упал: длина прыгнула с 1 клетки обратно на 6. Причина не баг, а
  реальное устройство перевозки: `arriveAtPickup` выдаёт слуге **новый**
  путь для второго плеча (обратно на склад с грузом) в тот же самый тик,
  когда путь первого плеча опустошается — `RemainingPath()` никогда не
  видит настоящий 0 между двумя плечами. Тест поправлен: монотонность
  проверяется только **внутри одного и того же** `s.State()` — смена
  состояния (значит, действительно началось новое плечо) законно
  сбрасывает отсчёт. Остальные шесть типов не продублированы отдельными
  тестами — реализация идентична (тот же `path[pathIdx:]`), возиться с
  шестью копиями одного и того же теста лишнее.
- **Как проверялось визуально** — тем же способом, что и автопереходы/
  декор выше: временная программа (`cmd/routepreview`, не часть
  репозитория), реально прогонявшая `logistics.Controller` через
  настоящее назначение работы слуге (та же связка склад+ферма+дорога,
  что и в `TestController_CollectsFromProducerToWarehouse`), пока слуга
  не оказывался посреди маршрута, затем сохранявшая кадр в PNG.

### Отдельная настройка масштаба камеры

Первый пункт из ROADMAP.md "После интерфейсного этапа" — колесо мыши
(`Camera.ZoomAt`) остаётся, но на вкладке "Опции" теперь есть ряд из 5
кнопок-пресетов (60%/100%/150%/200%/250%, `ui.ZoomPresets`), тем же
визуальным языком, что и ряд скорости прямо над ним.

- **`Camera.SetZoom`** — не переиспользует `ZoomAt` напрямую: `ZoomAt`
  привязывает зум к точке под курсором (осмысленно для колеса мыши,
  курсор реально стоит над картой), а клик по кнопке в панели — нет
  точки над картой, к которой можно привязаться. `SetZoom` вместо этого
  держит неподвижным **центр текущего вьюпорта** — тот же приём, что и у
  `ZoomAt` (пересчитать мировую точку под якорем до смены `Scale`, затем
  восстановить её после), просто с другим якорем. Общий `[minZoom,maxZoom]`
  clamp — те же границы, что и у колеса мыши, кнопка не может увести
  зум туда, куда не может увести и колесо.
- **Подсвечивается ближайший пресет, не только точное совпадение.**
  Игрок может поставить зум колесом мыши на значение, которое не
  совпадает ни с одной кнопкой — `closestZoomPreset` находит ближайшую
  по модулю разницы, чтобы ряд кнопок не выглядел так, будто вообще
  ничего не выбрано.
- Покрыто `internal/render/camera_test.go`
  (`TestCamera_SetZoom_KeepsViewportCenterFixed`,
  `TestCamera_SetZoom_ClampsToRange`) — реально проверяет, что мировая
  точка под центром экрана не сдвигается при смене зума, не просто что
  `Scale` поменялся.

### Тени зданий

Второй пункт. Осмотр реального исходного арта показал разнобой: часть
зданий (Warehouse, Bakery — судя по всему, более ранняя партия
генерации) уже несёт мягкую тень прямо в изображении, часть (Smeltery,
LumberjackHut, CarpentryWorkshop — судя по всему, более поздняя, куда
более детальная партия) — нет вообще, плоско висит на прозрачном фоне.
Из-за этого разные виды зданий выглядели непоследовательно "привязанными
к земле" — одни с тенью, другие без, без какой-либо логики, зависящей
от вида здания, а не от партии генерации.

- **`assets.BuildingShadow`** — одна процедурная полупрозрачная эллипс-тень
  с мягким краем (радиальное затухание альфы от центра, растеризована
  один раз при старте — тот же приём, что и `assets.RoadFadeN`/
  `assets.IdleCloud`), рисуется **под каждым** стоящим зданием
  одинаково, независимо от того, что там в исходном арте — так и разнобой
  исчезает, и здания, у которых тени не было вовсе, наконец выглядят
  стоящими на земле, а не приклеенными.
- Рисуется `render.drawBuildingShadow` в общем цикле `DrawBuildings`,
  сразу после проверки "не стройплощадка" и **до** `switch b.Kind` —
  единая точка для всех видов сразу, а не по копии на каждый case.
  Явно пропускает `Tree`/`Fish`: природные объекты уже "заземлены"
  собственным многостадийным спрайтом, добавлять им искусственную
  тень здания было бы лишним.
- Позиционирование — тот же нижний край клетки, к которому
  `drawStandingScaled` крепит низ стоящего спрайта (`sy+tilePixels-h`),
  так что тень заведомо совпадает с тем местом, где спрайт визуально
  касается земли, а не плавает отдельно от него.

### Мелкий декор: зоны

Третий пункт — пользователь уточнил, что имеет в виду не единичные
декорации (уже сделаны, см. "Мелкий декор" выше), а что-то покрупнее:
отдельные зоны/ландшафтные элементы. Добавлено поверх существующего

— грубая (`decorZoneSize=12` клеток) сетка "флейвора", тем же
детерминированным хэшем от координат, что и весь остальной декор, так
что ничего нового в `save.GameState` заводить не пришлось — луг/каменистый
участок/обычная трава восстанавливаются из одних только координат клетки
при каждой перезагрузке. Большинство ячеек — обычная трава (~65%); меньшая
часть читается как отдельный луг (плотность decorа ×3, уклон в сторону
цветов/кустов) или каменистый участок (та же плотность, уклон в сторону
камней/пней) — тот же дух, что и у `seedThickets` (плотные скопления
деревьев поверх равномерного разброса), но посчитано во время отрисовки,
а не расставлено настоящими объектами мира: у грядки цветов нет
геймплейного веса, который оправдывал бы это.

- **Проверено числами, не только скриншотом.** Разница в плотности x3
  и уклон варианта декорации на глаз почти не читаются в скриншоте —
  отдельные точки слишком малы и теряются в шуме травяной текстуры,

  `internal/render/decor_zone_test.go`, которая реально считает
  плотность и состав вариантов на выборке 400×400 клеток и
  подтверждает и ×2+ плотность, и ≥80% уклон в сторону нужного
  варианта — то, что скриншот подтвердить не может.
- Заодно поднялся реальный, отдельный от зон момент: цвет камня
  (120,118,112) оказался слишком близко по тону к собственной

### Спрайты юнитов смотрят в сторону движения

Четвёртый, последний пункт. Каждый из семи типов юнитов сейчас — одна
статичная поза (`assets.staticFrames` буквально повторяет один и тот же
кадр трижды в "анимационном" массиве — цикл кадров в рендере ничего не
меняет, кроме bob'а), нарисованная лицом в одну фиксированную сторону —
без нового арта эту позу физически нечем заменить. Что можно сделать без
новых кадров — переворачивать существующий спрайт по горизонтали лицом
по направлению движения, чего раньше не было вовсе (юнит, идущий влево,
всё равно был нарисован в исходной "художник рисовал вправо" позе).

- **`render.facingLeft(x, y int, path []pathfind.Point) bool`** —
  выводится из уже существующего `RemainingPath()` (добавлен в этом же
  заходе для линии маршрута выше) сравнением текущей клетки с первой
  клеткой оставшегося пути: ни одного нового поля ни в одном из семи
  пакетов профессий заводить не пришлось. Нет пути (простой юнит, юнит
  на посту) — исходная ("вправо") ориентация остаётся, разворачивать
  нечего.
- **`render.drawStandingFacingScaled`** — `drawStandingScaled` с
  опциональным зеркалированием через отрицательный X-масштаб
  `GeoM.Scale(-scale, scale)`; поскольку отрицательный масштаб растит
  изображение в другую сторону от локального начала координат, точка
  `Translate` для отражённого случая — **правый**, а не левый край той
  же итоговой рамки, что и у обычного случая (иначе конечная позиция
  на экране сместилась бы, а не просто отразилась на месте).
  `drawStandingScaled` без флага стала тонкой обёрткой над этой функцией
  с `flip=false`, чтобы не дублировать код.
- Применено единообразно во всех семи `render/*.go` (слуга, villager,
  лесоруб, рыбак — обе ветки, пешая и на лодке, каменотёс, строитель,
  рудокоп) — тем же способом, что и `RemainingPath()` раньше в этой же
  сессии.
- **`facingLeft`** покрыт `internal/render/sprite_test.go`
  (`TestFacingLeft`) — чисто логическая функция, без графического
  контекста. Сам переворот спрайта проверен визуально: временная
  программа (`cmd/facingpreview`, не часть репозитория) прогоняла два
  реальных сценария Controller.Tick (склад западнее фермы и склад
  восточнее фермы) до состояния "слуга посреди маршрута", подтвердила
  скриншотом, что идущий на запад слуга зеркально отражён, а идущий на
  восток — нет.

### Реальный баг: полноэкранный режим — карта в верхнем левом углу

После перехода на полноэкранный запуск (`ebiten.SetFullscreen(true)` в
`main()`) главное меню отображалось нормально, а игровая карта (`screenPlay`)
уезжала в верхний левый угол экрана, а справа и снизу оставалась чернота.

**Причина**: `ebiten.WindowSize()` в полноэкранном режиме отдаёт устаревший
логический размер (это уже было задокументировано у полей `frontWidth` /
`frontHeight` структуры `Game`), а `Game.Update()` пересчитывал раскладку
именно через него каждый кадр — `Layout(outsideWidth, outsideHeight)` тоже
не гарантированно успевает подхватить актуальный размер. Титульный экран уже
решал эту же проблему: `drawFrontScreen` читает `screen.Bounds()` прямо
внутри `Draw()` — это всегда настоящий размер буфера, в который вот-вот
нарисуется кадр. У игрового экрана такой подстраховки не было вовсе.

**Исправлено** тем же приёмом в `Game.Draw()`: если `g.screen == screenPlay`,
перед отрисовкой читается `screen.Bounds()` и, если он не пуст, вызывается
`g.resizeLayout(bounds.Dx(), bounds.Dy())` — тем самым игровой экран
досамостоятельно поправляет раскладку каждый кадр, а не полагается
исключительно на `Update()`.

### Реальный баг: демо-посёлок на титульном экране не был подключён к дорогам

Пользователь пожаловался: демка на главном экране "кривая", "деревня
мёртвая". Проверка (`internal/building/types.go`: ни у одного из типов
зданий в демо-посёлке `AccessX`/`AccessY` не заданы — значит точка входа
это сама клетка `(X, Y)`, т.е. верхний левый угол постройки) показала: **ни

### Реальный баг: деревья вырастали внутри непроходимого скопления

Пользователь: "сделай чтобы ресурсы спавнились без дыр! а то дерево
выростает внутри и к нему невозможно подойти."

**Причина**: и первичная генерация зарослей (`growThicketZone`), и
досев одиночных деревьев (`seedTrees`), и возрождение вырубленных
(`findTreeSpawnCell`) проверяли только `building.CanPlace` — свободна ли
сама клетка под дерево. Ни один из трёх ни разу не проверял, сможет ли
кто-то вообще ДОЙТИ до этой клетки. `pathfind.FindLandPath` разрешает
зайти на клетку цели (дерева), даже если она обычно считается
препятствием — иначе лесоруб в принципе не мог бы дойти до дерева — но
каждая клетка ПЕРЕД ней всё ещё должна быть проходимой (не занятой другим
зданием/деревом, не водой). У дерева, окружённого другими деревьями со
всех 8 сторон (типичная ситуация внутри плотных зарослей `growThicketZone`,
где соседние клетки массово заполняются деревьями), таких клеток просто не
остаётся — оно физически недостижимо, хотя формально "существует".

**Исправлено**: `cmd/game/main.go`, три новые функции —
`treeCellHasOpenNeighbor` (проверяет по тем же правилам, что и
`pathfind.landWalkable`: дорога проходима, любое другое здание/дерево —
нет), `treeAt` и `treePlacementKeepsEveryoneReachable` — итоговая проверка
перед посадкой дерева, которая смотрит не только на саму новую клетку, но
и на то, не отрежет ли эта посадка последний свободный сосед у уже
стоящего рядом дерева (иначе баг просто переехал бы на соседа вместо того
чтобы исчезнуть). Подключено во всех трёх местах: `seedTrees`,
`growThicketZone`, `findTreeSpawnCell`. Закреплено
`TestSeedThicketsNeverStrandsATree` (ни одно дерево из сгенерированных
зарослей не должно остаться без проходимого соседа) и
`TestTreePlacementKeepsEveryoneReachable` (прямая проверка функции: клетка
в кольце из 8 деревьев отклоняется; посадка, которая отрезала бы
единственный открытый сосед у существующего дерева, тоже отклоняется).

Каменные/рудные залежи и рыба намеренно не тронуты: рыбак ловит с лодки
(не подходит по суше вплотную к самой рыбе), а залежи — не единичные
объекты, а целые области клеток одного типа, куда каменотёс/рудокоп идёт
на любую ДОСТИЖИМУЮ клетку из региона, а не обязательно на каждую
конкретную — тот же класс бага здесь настолько же вероятен не был.

### Плотность залежей камня/руды — прямой процент вместо двух слоёв

Раньше плотность залежей считалась в два слоя: случайный процент площади
(например, уголь 4-8%) умножался на отдельный понижающий коэффициент
(`oreDepositGenerationPercent`/`stoneDepositGenerationPercent`, 70%/40%).
По запросу пользователя оба слоя схлопнуты в один: `coalMinPercent`,
`ironOreMinPercent`, `goldOreMinPercent`, `stoneMinPercent` и их `Max`-пары
теперь задают итоговый процент площади напрямую, без скрытого множителя
— `scaledDepositCells`/`scaledStoneDepositCells` это просто
`area * percent / 100`.

Новые значения (по прямому запросу): камень 3-4%, уголь 2-3%, железная и
золотая руда — **обе фиксированы на 1%** (не диапазон, а конкретное
значение: `Min == Max`) — раньше золото было редким подмножеством
диапазона железа, пользователь явно попросил их уравнять.

Одновременно `building.StoneDepositReserve`/`OreDepositReserve` подняты
с 10000 до 15000 за клетку ("поместим в 1 клетку не 10к, а 15к ресурсов,
это позволит нам сократить общее количество клеток") — итоговый суммарный
запас на карте остаётся примерно того же порядка, а количество отдельных
клеток-залежей (визуальный "мусор" на карте) при этом падает.

**Контекст, почему это ни на что не влияет с точки зрения "хватит ли"**:
один рабочий тратит 1 Reserve за 12 тиков (6 сек на обычной скорости) — то
есть даже одну клетку при 15000 Reserve один рабочий вырабатывает под
25 часов непрерывной добычи. Истощение залежей физически недостижимо в
рамках любой разумной игровой сессии что при 10к, что при 15к за клетку —
этот параметр меняет только визуальную плотность точек на карте, не
реальный запас ресурсов.

Тесты `TestSeedStoneDepositsSplitsAcrossMultipleRegions`,
`TestSeedOreDepositsRespectsDesignedAbundance`,
`TestScaledDepositCellsApplyPercentDirectly` (переименован из
`...UseResourceSpecificDensity`) обновлены под новую формулу и новое
равенство железа с золотом.

### Реальный баг: одинаковые по приоритету постройки всегда решались по порядку в срезе

Найдено симуляцией реального сохранения пользователя (не синтетическим
тестом): при равном приоритете `findTavernSupplyJob`, `findCollectJob`,
`findDirectJob` (сторона потребителя) и `findSupplyJob` всегда выбирали
**первого подходящего кандидата в порядке `buildings` slice**, а не того,
у кого реально больше накопилось (`have`) или он больше нуждается
(`short`). На практике порядок в `buildings` — это, как правило, порядок
постройки, так что более РАННЯЯ постройка того же вида систематически
выигрывала конкуренцию за слугу у более ПОЗДНЕЙ, независимо от того, у
кого реально больше скопилось груза.

**Исправлено** во всех четырёх функциях: при равенстве приоритета теперь
побеждает больший `have`/`short`, а не позиция в срезе. У
`findTavernSupplyJob` раньше вообще не было никакого сравнения — просто
`return` на первом подходящем; переписано на сбор кандидатов + сортировку
по `have` (`slices.SortFunc`) перед проверкой достижимости.

**Стоимость по производительности — нулевая или отрицательная (дешевле,
не дороже)**: во всех четырёх местах дорогой `pathfind.FindPath*` (BFS)
теперь вызывается **реже**, а не чаще — кандидат, проигравший сравнение
по `have`/`short`, отсеивается ДО вызова BFS, а не после (раньше BFS
вызывался на каждом кандидате по порядку, пока не найдётся первый
проходимый). У `findTavernSupplyJob` добавлена сортировка небольшого
списка кандидатов (обычно единицы построек одного вида) — тоже
незначительно по стоимости на фоне самого BFS.

Закреплено `TestController_TavernSupplyPrefersBiggestBacklog` (новый) и
обновлены `TestController_PriorityBreaksDirectHaulTie`/
`TestController_PriorityBreaksSupplyTie` — они раньше явно проверяли
старое поведение "без приоритета побеждает первый по порядку", теперь
проверяют "без приоритета побеждает более нуждающийся".

**Важная оговорка, найденная контрольной симуляцией после фикса**:
винодельни в реальном сохранении пользователя (простаивали 16-24% времени
при любом числе слуг — от 27 до 110) остались простаивать почти так же и
ПОСЛЕ этого фикса. Перепроверка показала: дело не в нечестном выборе
между винодельнями (они все на разном, не совпадающем расстоянии друг с
другом, конкурировать за "одинаковую" позицию им особо не с кем) — дело в
том, что `Winery.OutputCapacity` (8) **точно равен** `OutputAmount` (8):
буфер выскакивает с 0 до 100% одним махом каждый цикл, и после этого
неизбежно "простаивает полным", пока слуга физически не дойдёт туда —
а это чистая физика (время в пути), не баг и не нечестный выбор. Для
ближней винодельни (9 клеток) минимальное время ожидания ~7.5% от цикла
производства, для дальней (29 клеток) — ~24%: наблюдаемые числа
практически совпадают с этим теоретическим минимумом. Ничего не
теряется (это пауза производства, не потеря готового вина) — раз это не
баг, трогать не стал. Остальные виды построек (Ферма, Мельница, Пекарня,
Свиноферма, Мясной цех) показали 0% простоя у каждого экземпляра — их
объём одной партии всегда меньше буфера, так что этот эффект их не
касается вовсе.

**Дальше пользователь всё же попросил поправить именно этот механизм** —
не в логистике, а в самом рецепте. Ферма и винодельня раньше отдавали
весь урожай одним махом в конце цикла (Ферма: 5 пшеницы за 120 тиков;
Винодельня: 8 вина за 240 тиков) — именно это "всё сразу" и создавало
мгновенный скачок буфера до 100%, разобранный выше. По прямому запросу
("чтобы за раз не сразу восемь единиц продукции попадало... а условно
давать по два... цикл производства немного увеличится") оба рецепта
переписаны на маленькие частые партии: Ферма — 2 пшеницы за 60 тиков
(было 5/120, значит по факту чуть медленнее суммарно), Винодельня — 2
вина за 72 тика (было 8/240). Логика уже существовала в движке
(`tickRecipe` и так зацикливает один и тот же рецепт бесконечно) — само
изменение это просто новые числа в `internal/building/types.go`, без
новой механики. `OutputCapacity` винодельни (8) не трогал: с партиями по
2 это уже запас на 4 несобранных цикла, а не мгновенное "под завязку".

задержка и разрыв с архитектурой; вместо этого — обычный эвристический
пакет, architecturally не отличающийся от `economy`/`logistics`/`builder`.

`internal/advisor` — чистая логика без ebiten, `Evaluate(...) []Tip`, без
собственного состояния (кулдауны/очередь/троттлинг — забота `cmd/game`,
не пакета). Четыре правила, как попросил пользователь:

1. **Еда на исходе** — суммарный запас еды (склад + все харчевни) делится
   на темп потребления населения (`pop.Count / hunger.MealThresholdTicks`
   — 1040, момент похода в харчевню при 20% сытости). Сознательно **не
   учитывает будущее производство** — это "на сколько хватит текущего
   запаса, если ничего не изменится", а не прогноз с доходом: честнее (не
   обещает, что подвоз спасёт, если сам под вопросом) и не требует
   моделировать темп фермы/винодельни отдельно. Порог — 350 тиков
   (середина запрошенного диапазона 300-400).
2. **Пустующее здание** — тот же сигнал, что уже красит здание на карте
   (`unstaffedWorkerBuildings()`), но только если простаивает дольше 200
   тиков подряд (не дёргать сразу после постройки, пока игрок идёт
   нанимать).
3. **Не подключено к дороге** — переиспользует уже существующий
   `disconnectedBuildings()`.
4. **Слуг мало/много** — сравнение с `recommendedServeCount()` (уже
   сделан в этой сессии). Пороги намеренно несимметричны: "мало" — 70% от
   рекомендации (реальная проблема с производством), "много" — 200%
   (лишние слуги почти безвредны, просто потрачено золото) — не дёргать
   по мелочи сразу после найма про запас.

И пустующие, и неподключённые постройки одного типа за раз агрегируются в
**одну** подсказку (`Count` + один пример), а не спамят по зданию.

5. **Работник-добытчик не может найти сырьё** — добавлено по отдельному
   запросу пользователя: лесоруб/каменотёс/рудокоп не находят рядом
   дерево/камень/руду. У всех трёх профессий свой `State()`/`StateIdle`
   (разные типы в разных пакетах, не общий интерфейс) — простой в этом
   состоянии обычно длится один-два тика (тут же находится новая цель),
   так что затянувшийся простой именно в `StateIdle` (не "занят
   разгрузкой", не "идёт есть") — надёжный сигнал, что рядом реально
   ничего не осталось. Порог — 650 тиков (середина запрошенного
   диапазона 600-700), `GatherWorkerStuckWarningTicks`. Трекер
   (`advisorGatherStuckSince`, `trackAdvisorGatherWorkers`) — точная
   копия уже существующего трекера для пустующих зданий
   (`advisorIdleSince`), логика агрегации в самом `Evaluate` вынесена в
   общую `evaluateSinceMap`, переиспользуемую обоими правилами.

**Троттлинг** — в `cmd/game`, не в пакете: полная проверка раз в 300
тиков (`advisorCheckIntervalTicks`), у каждого вида подсказки свой
кулдаун 1500 тиков после того, как игрок нажал "Ознакомлен" (не
сбрасывается сама, если проигнорирована — ждёт в очереди). Одновременно
на экране не больше одной подсказки, остальные — в FIFO-очереди
(`g.advisorQueue`). Состояние не сохраняется в save-файл — тот же
принцип, что уже применён к погоде/освещению (см. выше): не мировая
механика, не должна попадать в формат сохранения.

**UI** — не модальный диалог (`ui.DialogKind` блокирует остальной ввод),
а отдельная плашка поверх карты (`ui.DrawAdvisorToast`) с кнопкой
"Ознакомлен" — игрок продолжает играть, доска не обязана ждать клика.
Клик по кнопке проверяется в `handleLeftClick` раньше даже миникарты —
плашка рисуется поверх всего, значит и клик должен доставаться ей первой.

Формула запаса еды проверена на реальном сохранении пользователя (тем же
способом, что и предыдущие эвристики в этой сессии): при населении 151 и
принудительно уменьшённом запасе (5 хлеба, харчевни опустошены) —
подсказка сработала с `TicksLeft=34`, что в точности совпадает с ручным
расчётом (5 × 1040 ÷ 151 ≈ 34.4).

### ПКМ по слуге сокращает до рекомендованного числа

По запросу пользователя правый клик по карточке "Слуга" во вкладке
Юниты научился сокращать сразу до `recommendedServeCount()`, а не по
одному слуге за клик. Дважды уточнялось поведение по ходу разговора:

1. Сначала: сокращает всех лишних сразу одним кликом
   (`trimSerfsToRecommended`).
2. Затем пользователь уточнил: если слуг уже меньше или ровно
   рекомендованного, ПКМ должен вести себя **как раньше** — увольнять
   ровно одного (`dismissOneSerf`), а не быть no-op'ом.
3. И ещё раз уточнил финальный UX: когда есть реальный избыток, сначала
   спросить — модальный диалог "слуг сейчас N, рекомендовано M, уволить
   всех лишних сразу?" с кнопками Да/Нет. **"Нет" — это не отмена, а
   отдельное действие**: увольняет одного, как обычно. Только Esc —
   настоящая отмена без побочных эффектов, как у всех остальных диалогов
   в игре (`DialogConfirmRemoval`, `DialogConfirmDemolitionMode`).

Новый `ui.DialogConfirmTrimServes` — переиспользует ту же геометрию
Да/Нет, что уже была у `DialogConfirmDemolitionMode`
(`InspectorConfirmRemoveRect`/`Buttons`), рисуется в пустом инспекторе
тем же способом. Увольнение в обоих случаях (по одному и до
рекомендации) идёт через уже существующий безопасный
`logistics.Controller.RequestDismissal` — слуга сначала заканчивает
текущий рейс, потом уходит, ничего не пропадает.

### Реальный баг: звук казался "выключенным" первые ~2 минуты новой игры

Пользователь: "почему-то при запуске игры звуки отключены, только музыка
играет, звуки нужно руками включать" — эмпирически нашёл, что помогает
клик по ползунку громкости звуков в паузе (Esc).

Громкость (`defaultSFXVolume=0.55`) была ни при чём — она верно
проставлена ещё на этапе инициализации пакета, до `main()`. Реальная
причина: `g.worldTicks` инкрементируется **в начале** каждого тика
(`g.worldTicks++` — первая строка внутри `for range g.sim.Advance()`),
значит после самого первого тика игры `g.worldTicks == 1`, а не `0` — он
никогда фактически не равен нулю во время реальной игры. Все периодические
проверки звука (`tickAudioCues`/`tickBuildingAmbientSounds`/
`tickWeatherAmbientSounds`/`tickDayNightAmbientSounds`/
`tickWindAmbientSounds`) были написаны как `worldTicks % period == 0` —
первое совпадение наступает только на тике `period`, а не сразу. При
`framesPerSimTick=30` и 60 FPS (2 тика/сек) для безусловного `PlayWind`
(`windAmbientPeriod=240`) это означает **2 реальные минуты полной тишины**
после старта новой игры, прежде чем прозвучит вообще хоть что-то, кроме
музыки. Пользователь не выдержал паузу, начал тыкать в меню — звук к тому
моменту как раз успевал зазвучать сам, что и создало иллюзию "нужно
включить руками".

Исправлено заменой всех этих проверок на общий хелпер
`(g *Game) onAudioPeriod(period int) bool { return g.worldTicks%period ==
1 }` — тот же период, но первое совпадение сразу на первом тике игры, а
не спустя период. Теперь безусловный `PlayWind` слышен в первую же
симуляционную секунду новой игры — то, что пользователь явно попросил
("нужно чтобы звуки при начале игры сразу были включены!").

### Реальный баг: громкость 0 не останавливала уже играющий звук

Пользователь: "почему я в настройках громкость музыки и звуков выставил в
0, но я все равно слышу свинью, проверь все звуки! ... если громкость в 0
- полная тишина!"

`SetSFXVolume` раньше только запоминала новое значение `sfxVolume` —
проверка `sfxVolume <= 0` в `playRandom` действительно не даёт запустить
ни один *новый* звук, но никак не трогает плеер, который уже играет (был
создан мгновением раньше, пока громкость ещё была не нулевой) — он
доигрывал на старой громкости до конца клипа. Для коротких SFX это почти
незаметно, но достаточно, чтобы породить впечатление "звук не слушается
настройки".

Исправлено: `internal/audio/audio.go` теперь ведёт `activeSFX
[]*audio.Player` — список ещё играющих одноразовых плееров (наполняется в
`playRandom`, самоочищается от уже доигравших через `trackSFXPlayer`).
`SetSFXVolume(0)` в дополнение к обнулению громкости сразу вызывает
`Pause()` у всех них и опустошает список — то есть 0 действительно
означает мгновенную полную тишину, а не только "новых звуков больше не
будет". У музыки это уже было устроено верно (`SetMusicVolume` и раньше
вызывала `musicPlayer.Pause()`), правили только сторону SFX. Новый тест
`TestSetSFXVolumeZeroStopsAlreadyPlayingSounds` фиксирует именно это
поведение на реальном звуке (`chopSFX`), не только на факте отсутствия
паники.

   - `internal/enemy`: `Enemy` получил `path`/`pathIdx`/`tileTicks`,

   - `internal/ui/panels.go`: `selectedUnitTile`/`drawSelectionIcon`-путь

   - `cmd/game/main.go`: `selectionAt` находит врага под курсором;

### Реальный баг: камень убивал раньше, чем долетал

Пользователь (тестирует через `go run`, не через `bin\`): "анимация полёта
камня в противника теперь совпадает с его смертью? Раньше было сперва
противник погибает, а потом летит камень в него".

Причина: `sentry.engage` ставил `target.HP = 0` **мгновенно**, в тот же
тик, что и выстрел, а `internal/render/projectiles.go` (визуал полёта
камня, добавлен Codex-ом) отдельно анимирует `shotVisualTicks` ещё
`shotVisualLifetime=6` тиков после этого. Из-за этого `pruneDeadEnemies`
удалял противника и запускал анимацию смерти (тоже от Codex,
`internal/render/deaths.go`) сразу же — раньше, чем камень визуально
долетал до цели.

Исправлено: `Sentry` получил `shotPendingTarget *enemy.Enemy` — момент
выстрела теперь только тратит камень, запускает визуал и ставит кулдаун,
а `target.HP = 0` применяется в `Controller.Tick`, когда `shotVisualTicks`
досчитывает до 0 (камень реально долетел). Цель всё это время остаётся
живой и взаимодействуемой (её можно двигать/выбирать, как обычно).
Новый прямой регрессионный тест
`TestSentry_KillNeverLandsBeforeTheStoneVisuallyArrives` проверяет именно
эту причинно-следственную связь через `ShotVisual()`, а не просто финальный
результат — старый баг он бы поймал.

### Проверка "codex удалил управление противником" — не подтвердилась

Отдельно пользователь сообщил, что Codex, рисуя спрайт смерти, якобы
удалил управление вражеским юнитом. Статическая проверка кода и новый
интеграционный тест `TestCommandSelectedEnemyTo_IssuesAMoveOrder`
(`cmd/game/main_test.go`, идёт через реальный вызов `camera.ScreenToTile`
→ `Enemy.MoveTo`, а не только `internal/enemy`'s собственный юнит-тест)
показали, что весь путь выбора/ПКМ-перемещения на месте и работает.
Возможная причина путаницы (позже не подтверждена и не опровергнута
пользователем) — устаревший `bin\strategy_game.exe`, собранный на день
раньше коммита с этой фичей; пользователь пояснил, что тестирует через
`go run`, так что это не окончательный ответ, если проблема повторится —
разбираться дальше.

### shotVisualLifetime: 6 → 1 тик

Пользователь: "проигрывай анимацию 1 тик, а то противник успевает сделать
несколько шагов до того момента пока камень летит, и по факту получается
что камень падает на одну клетку, а противник умирает на другой". За 6
тиков полёта движущаяся цель (см. `Enemy.MoveTo`) успевала сместиться на
несколько клеток относительно того места, где камень визуально
приземлялся. При 1 тике цели физически негде сдвинуться между выстрелом и
попаданием — камень и смерть снова совпадают по клетке, как и раньше
падение до этого исправления с мгновенным убийством. Все тесты
(`internal/sentry`) ссылаются на константу `shotVisualLifetime`
символически, поэтому изменение прошло без правки самих тестов.
